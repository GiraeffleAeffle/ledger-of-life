# Regional shared topics (Märkisch-Oderland)

Build from the repository root with **one command** (Node.js 22+):

```sh
npm --prefix stadtstack-data/regional run all
```

This installs the lockfile's dependencies and writes `stadtstack-data/out/regions/brandenburg-mol/topics.json`. Subsequent runs can use `npm --prefix stadtstack-data/regional run build`; `npm --prefix stadtstack-data/regional run build -- --offline` rebuilds from locally cached source bytes. `REGIONAL_AS_OF=2026-09-27` fixes the 18-month observation window for a dated research run. Cache and installed dependencies are ignored by Git. A fresh run fetches only public pages/API responses, sends `StadtstackResearch/1.0`, checks robots.txt and crawl delay, spaces requests per host, and uses last-good cache on transient source failures (reported in `coverage.warnings`). A source that changes its evidence phrase is *omitted*, not silently reasserted.

## `stadtstack-regional-topics-v1`

The standalone JSON object contains:

- `schemaVersion`, `generatedAt` (UTC publication instant), `asOf` (UTC observation date), `region` (`id`, `name`, `state`, `ags` district code, `sourceUrl`, `municipalityCount`, `centreMeaning`), `coverage` (the 18-month cutoff, observed source counts and warnings), and `sources` (upstream URL, type, rights/attribution and checks where known).
- `offices`: six official Ämter `{id,name,regionKey}`. `municipalities`: **all 45** official MOL municipalities `{id,name,ags,center:[longitude,latitude],centerPrecision,amtId?}`. IDs use lowercase ASCII, ä→ae, ö→oe, ü→ue, ß→ss, other-character runs→`-`, trimming ends. AGS is obtained from the Land's twelve-digit regional key as its first five plus last three digits. Centre coordinates are **approximate administrative-address points**, transformed from the official CSV UTM zone 33 values to WGS84; they are *not* municipal centroids, plan boundaries, or private locations. Original coordinates, names and keys: [Brandenburg Kommunalverzeichnis](https://service.brandenburg.de/service/de/adressen/kommunalverzeichnis/), **dl-de/by-2-0**, attributed to Service Brandenburg. Changes: MOL filtering, key derivation, coordinate conversion, and rounding. The official district [hierarchy](https://service.brandenburg.de/service/de/adressen/kommunalverzeichnis/ansicht/~12064-maerkisch-oderland) cross-checks membership and Amt relations.
- `cityRegions`: every municipality slug maps to `brandenburg-mol`. A consumer looks up its existing city slug here before showing an “In your region” card; unfamiliar cities get no claim of regional coverage. The mapping is in this file, not the city-data catalogue.
- `topics`: `{id,label,summary,categoryKeywords,municipalities,firstSeen,lastSeen,method,reviewState}`. A topic is published **only when at least two distinct municipalities** have source items. `municipalities[]` has `{municipalityId,stage,items:[{title,url,date,sourceType,locator,stage,...}]}`. `sourceType` is `planningProcedure`, `cityWebsite` or `councilAgenda`. `date` is a documented *event/start/meeting date*, or `null` when only a month/undated current page is known; it is not ingestion time. `firstSeen`/`lastSeen` are minimum/maximum known item dates, not first crawl dates. `stage` is evidence-specific (`adopted`, `decision_recorded`, `evaluation`, `decision_pending`, `consultation_closed`, `consultation`, `draft`, `planning`, `referred`, `agenda`, `unknown`); only an expressly adopted plan is `adopted`. `consultation_closed` means only that a listed participation period ended; it is **not** adoption. A `decision_recorded` agenda item says a particular vote took place, not that all infrastructure was built or the wider topic completed. Topic municipality stage is the strongest *item-specific* stage in its group; inspect individual `items[].stage` for meaning. No ranking should interpret an agenda as a decision.

## Extraction boundaries

`build.mjs` verifies the official municipality register and URL/locator phrases in `city-evidence.json`, reads a bounded set of public Hoppegarten SessionNet agendas, checks Wriezen's allowed calendar feed only for counts (committee names cannot establish policy topics), and queries the public statewide DiPlan procedure listing. DiPlan procedure titles are indexed with dates, phase, city link and precise API locator; plan geometry can be inspected upstream but is **not redistributed** without verified rights. Some DiPlan place fields describe an Ortsteil, not the responsible municipality, and a shared Seelow-Land operator label covers unrelated towns; municipality matching therefore requires an unambiguous official name in the title/organization or validated place matching. Generic “Bebauungsplan” alone is not a shared topic.

`taxonomy.mjs` holds the auditable German keyword categories and TF-IDF/cosine title grouping for uncategorized procedure titles. `method:'keyword'` is a category match; `method:'cluster'` signals an unreviewed similarity hypothesis, not a confirmed common project; no LLM is needed and no text is represented as reviewed. Short summaries are independently written factual interpretations; **every topic is `reviewState:'candidate'`** pending editorial assessment. Do not reuse full council papers, PDFs, image/map assets or procedure prose from this output. City/RIS/DiPlan reuse terms have not been shown to permit bulk redistribution: this is an attributed short-title/factual-source index, **not** an openly licensed clone of their archives. The MOL OParl System explicitly says `Nutzung nur nach Genehmigung` and its host disallows crawling; it is not ingested.

Upstream source checks and substantive cross-city examples are in [regional research findings](../../docs/research/BRANDENBURG_SHARED_TOPICS.md). The file is public regional context only; it never includes resident addresses or interests.
