# Regional shared topics (Märkisch-Oderland)

Rebuild from existing local snapshots only (Node.js 22+):

```sh
npm --prefix stadtstack-data/regional run all -- --offline
```

This installs the lockfile's dependencies and writes `stadtstack-data/out/regions/brandenburg-mol/topics.json` from already available `regional/.cache` snapshots. Subsequent runs use `npm --prefix stadtstack-data/regional run build -- --offline`. The standalone entrypoint requires exactly `--offline`; absent, unknown or live-mode arguments fail before source reads. All live fetch, cache-refresh and last-good network fallback code has been removed. Missing snapshots never trigger a request. New acquisition must use the governed district lane, not this historical cache format. `REGIONAL_AS_OF=2026-09-27` fixes the 18-month observation window for a dated research run. Cache and installed dependencies are ignored by Git. A cached source that changes its evidence phrase is omitted, not silently reasserted.

## `stadtstack-regional-topics-v1`

The standalone JSON object contains:

- `schemaVersion`, `generatedAt` (UTC publication instant), `asOf` (UTC observation date), `region` (`id`, `name`, `state`, `ags` district code, `sourceUrl`, `municipalityCount`, `centreMeaning`), `coverage` (the 18-month cutoff, observed source counts and warnings), and `sources` (upstream URL, type, rights/attribution and checks where known).
- `offices`: six official Ämter `{id,name,regionKey}`. `municipalities`: **all 45** official MOL municipalities `{id,name,ags,center:[longitude,latitude],centerPrecision,amtId?}`. IDs use lowercase ASCII, ä→ae, ö→oe, ü→ue, ß→ss, other-character runs→`-`, trimming ends. AGS is obtained from the Land's twelve-digit regional key as its first five plus last three digits. Centre coordinates are **approximate administrative-address points**, transformed from the official CSV UTM zone 33 values to WGS84; they are *not* municipal centroids, plan boundaries, or private locations. Original coordinates, names and keys: [Brandenburg Kommunalverzeichnis](https://service.brandenburg.de/service/de/adressen/kommunalverzeichnis/), **dl-de/by-2-0**, attributed to Service Brandenburg. Changes: MOL filtering, key derivation, coordinate conversion, and rounding. The official district [hierarchy](https://service.brandenburg.de/service/de/adressen/kommunalverzeichnis/ansicht/~12064-maerkisch-oderland) cross-checks membership and Amt relations.
- `cityRegions`: every municipality slug maps to `brandenburg-mol`. A consumer looks up its existing city slug here before showing an “In your region” card; unfamiliar cities get no claim of regional coverage. The mapping is in this file, not the city-data catalogue.
- `topics`: `{id,label,summary,categoryKeywords,municipalities,firstSeen,lastSeen,method,reviewState}`. A topic is published **only when at least two distinct municipalities** have source items. `municipalities[]` has `{municipalityId,stage,items:[{title,url,date,sourceType,locator,stage,...}]}`. `sourceType` is `planningProcedure`, `cityWebsite` or `councilAgenda`. `date` is a documented *event/start/meeting date*, or `null` when only a month/undated current page is known; it is not ingestion time. `firstSeen`/`lastSeen` are minimum/maximum known item dates, not first crawl dates. `stage` is evidence-specific (`adopted`, `decision_recorded`, `evaluation`, `decision_pending`, `consultation_closed`, `consultation`, `draft`, `planning`, `referred`, `agenda`, `unknown`); only an expressly adopted plan is `adopted`. `consultation_closed` means only that a listed participation period ended; it is **not** adoption. A `decision_recorded` agenda item says a particular vote took place, not that all infrastructure was built or the wider topic completed. Topic municipality stage is the strongest *item-specific* stage in its group; inspect individual `items[].stage` for meaning. No ranking should interpret an agenda as a decision.

## Extraction boundaries

`build.mjs --offline` verifies cached official municipality-register and URL/locator phrases in `city-evidence.json`, reads cached public Hoppegarten SessionNet agendas, checks Wriezen's cached calendar feed only for counts (committee names cannot establish policy topics), and processes cached public statewide DiPlan listings. It performs no acquisition. DiPlan procedure titles are indexed with dates, phase, city link and precise API locator; plan geometry can be inspected upstream but is **not redistributed** without verified rights. Some DiPlan place fields describe an Ortsteil, not the responsible municipality, and a shared Seelow-Land operator label covers unrelated towns; municipality matching therefore requires an unambiguous official name in the title/organization or validated place matching. Generic “Bebauungsplan” alone is not a shared topic.

Curated website items now carry an extractive `statement` separately from their navigation `locator`. `statementEvidence[]` stores each complete source block as `{quote,sourceSha256,textNormalization:"html-whitespace-v1"}`; the hash binds the fetched HTML bytes and the normalization decodes HTML text and collapses whitespace. `city-evidence.json` may supply `statementAnchors[]`; otherwise its existing `evidence` phrase selects the unique complete paragraph/list/table-definition block. Missing or ambiguous matches are withheld, never reconstructed from a heading. The canonical consumer contract is `src/regional-statement.ts`: the statement must equal its bounded excerpts joined by blank lines, all from the same snapshot. Historical locator-only items remain readable but expose `statement:""`, `statementStatus:"not_extracted"` and the separate locator; they do not acquire invented factual text.

Shape agreement between a statement, its quotes and a claimed hash is not verification. `normalizeRegionalPublication` is asynchronous and verifies each statement against retained HTML returned by an authoritative, current-policy-gated URL/hash resolver. `verifyRegionalStatementSnapshot` recomputes the actual byte hash, checks the exact source URL, and requires every excerpt to be a complete block produced by the same HTML normalization used at extraction. A missing resolver or snapshot quarantines the statement-bearing item; wrong URLs, hashes or invented excerpts are likewise withheld. Current-policy lookup failures abort publication, never authorize cached reuse. Legacy locator-only rows require no fabricated snapshot or verification receipt.

The shared `REGIONAL_EXCERPT_LIMITS` is a conservative product publication policy, **not** a legal permission claim: at most six complete excerpts, 600 characters per excerpt and 1,800 characters in the assembled statement. Selected prose must not exceed half of its containing article's normalized prose (falling back to `main` or `body` when no article is marked); unrelated page content cannot justify copying an entire marked article. Both collection and retained-byte publication verification enforce these limits. Whole articles, excessive prose and oversized blocks are withheld, never truncated to discard qualifiers or squeeze through the gate.

Released regional stages retain separate `stageQuote` provenance from their source locator. Milestone aggregation labels this basis `released_structured_stage`, not a verbatim substantive claim. Thus a historical locator-only item can still carry its already released stage/date without turning its locator into a statement or dropping that milestone.

The Rüdersdorf and Hoppegarten heat-planning findings require new governed source acquisition and Codex-only extraction before a release can claim their detailed facts or all five memberships. Exact source IDs, URLs and acceptance requirements are in `reports/patch-0.3.2-heat-source-requirements.json`. These are acquisition requirements, not source quotes or a receipt of completed extraction. Do not patch frozen published output or historical model receipts. The legacy regional collector is not the governed acquisition entry point for that release work.

`taxonomy.mjs` holds the auditable German keyword categories and TF-IDF/cosine title grouping for uncategorized procedure titles. `method:'keyword'` is a category match; `method:'cluster'` signals an unreviewed similarity hypothesis, not a confirmed common project; no LLM is needed and no text is represented as reviewed. Short summaries are independently written factual interpretations; **every topic is `reviewState:'candidate'`** pending editorial assessment. Do not reuse full council papers, PDFs, image/map assets or procedure prose from this output. City/RIS/DiPlan reuse terms have not been shown to permit bulk redistribution: this is an attributed short-title/factual-source index, **not** an openly licensed clone of their archives. The MOL OParl System explicitly says `Nutzung nur nach Genehmigung` and its host disallows crawling; it is not ingested.

Upstream source checks and substantive cross-city examples are in [regional research findings](../../docs/research/BRANDENBURG_SHARED_TOPICS.md). The file is public regional context only; it never includes resident addresses or interests.
