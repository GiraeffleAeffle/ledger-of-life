# Stadtstack: rebuild the civic-data pipeline

**Planning snapshot: 11 October 2026. Status: proposal for implementation, not an implemented or benchmarked pipeline.** The owner approved the code-only direction after the value test. This document authorizes no collection, provider calls, expenditure, deployment or expansion. The actively changing `civic-pilot-value/stadtstack-data` repository remains read-only for this planning task; its 0.3.1/0.3.2 releases are separate work, not names reserved for R1–R4.

## 1. Decision and evidence

**Build a deterministic data pipeline with small, bounded model decisions—not an agent that operates the pipeline.** Buy information before buying more extraction: source-native identifiers, operators, permits, funding operations and financial document chains are the first investment. Then reduce inference through recall-first triage and evidence selection. Finally make the same jobs durable, incremental and replayable.

The required information is a set of **typed, evidenced chains**, not a single progress score:

- plan → deliberation/adoption → permit/conditions → procurement/award → actual construction/operation;
- budget appropriation → subsidy approval → payment/actual expenditure → delivered output → measured result;
- objection → responsible authority → disposition → condition/change → evidenced fulfillment;
- project/facility → operator/legal entity; operation → funding programme and funding period.

These chains are often branches, not a linear ladder. An adopted heat plan is not a permit, a budget authorization is not a payment, and an opened playground is not additional Kita capacity. Statistical trends and modeled heat demand do not prove a project's impact.

## 2. Target architecture

### 2.1 State machine and branch contracts

```text
Discovery → Policy/origin → Hash/CAS → Text/OCR or structured parse
  → Rules/triage → Evidence selection → Residual LLM extraction (only if needed)
  → Gates/judge → Case linking/entity resolution → Graph/manifest → MCP release
```

Every arrow is an explicit, versioned job result. `blocked_policy`, `blocked_access`, `held_origin`, `held_quality`, `deferred`, `failed_execution` and `superseded` are distinct outcomes. A valid `no_supported_case` is neither a crash nor proof of irrelevance. A structured record follows the same provenance and admission path but skips unnecessary OCR, triage, generation and semantic judging of directly coded fields.

| Step | Input → durable result | Proposed module / reuse |
| --- | --- | --- |
| Discovery | Catalog/registry snapshot + bounded scope + cursor → discovered resources, parent links, native IDs, next cursor, completeness receipt | Extend existing `district-source-adapters.ts` and `district-crawl.ts`; new `district-adapter-contract.ts` and `src/adapters/` |
| Policy/origin | URL/redirect chain + publicness + robots/TDM observations + issuer/work evidence + opt-out version → allowed/held/excluded decision and hash | New `district-policy.ts`, using the settled acquisition-policy/origin implementation from 0.3.1/0.3.2, not a second rights engine |
| Hash/CAS | Admitted response bytes → `sha256`, fetch/representation record, source-version binding | New `district-cas.ts`; reuse private-root constraints from `district-private-io.ts` and prepared-document handling |
| Text/OCR/parse | Bytes + parser/tool contract → text/table/features, immutable locators, quality/limits | Existing `district-document.ts`, `district-prepared-document.ts`; new adapter parsers and `district-evidence.ts` |
| Rules/triage | Metadata + eligible text/rows → retain/defer/audited-reject, topics, reason, probabilities | New `district-triage.ts`, `district-triage-eval.ts`; preserve topical vocabulary |

| Case/entity linking | Admitted claims + native identifiers + proposed matches → versioned identity links or unresolved candidates | New `district-case-linking.ts`, `district-entity-resolution.ts`; extend current identity contract, not an untracked side index |
| Graph/manifest | Admitted records + admitted identity assertions + scoped coverage → stable release artifacts | Extend existing `district-graph.ts`, `district-graph-query.ts`, `district-query.ts`, `district-publication.ts`, `data-release.ts` |
| MCP release | Verified immutable release + exact build identity → approved active manifest pointer | Reuse `mcp-release.ts`; existing release/publication path, no separate serving datastore |

**Policy-before-processing has a practical two-stage boundary.** Discovery first checks public access, opt-out and known resource origin. Where document-specific rights require inspecting headers/XMP/content, allow only a bounded private acquisition/inspection path under that policy. It is not admission to ordinary CAS processing, OCR, model calls or publication. Final origin/rights evidence must bind the exact received bytes before downstream admission. Unknown or mixed-origin content stays held; a host or official hyperlink cannot license a consultant's attachment. This avoids both an impossible “know the bytes before fetching” contract and an unrestricted fetch-first crawler.

Structured evidence is not turned into invented prose quotations. It references, for example, `{sourceSha256, format: 'xlsx', sheet, rowKey, cells, schemaHash}` or `{format: 'xml', nativeId, path, value}`. Code validates the original field and a versioned mapping rule. Text claims retain exact quoted spans. A new discriminated verification contract (`structured` versus `text_model`) is needed: **never invent a model name, faithfulness score or LLM receipt for deterministic parsing.** Narrative interpretation still uses the existing substantive gates. A parser mapping does not establish independent truth; it establishes faithful interpretation of an attributed source field.

**Parser/secret isolation is a separate security boundary.** The inspected `district-document.ts` subprocess launcher does not pass an explicit environment; do not reuse that behavior in a credential-bearing executor. `pdfinfo`, `pdftotext`, `pdftoppm`, `tesseract` and `python3` must run in **credential-free parse/OCR jobs** with an explicit environment allowlist: fixed trusted `PATH`, pinned UTF-8 `LANG`/`LC_ALL`, `TZ=UTC`, per-job empty `HOME` and private `TMPDIR`, and only required read-only tool-data paths such as `TESSDATA_PREFIX`. Never spread `process.env`; exclude provider keys, source-auth secrets, cloud credentials, proxy/auth variables, SSH agents and inherited descriptors. Python runs isolated from user packages/startup configuration. Inject a provider secret only into its model-job process, source authentication only into the particular authorized fetch job, and a scoped database credential only into the runner—not parser children.

Parsers receive read-only access to the selected input artifact and tool assets, a bounded writable scratch/output directory, and **no network**, home directory, credential mounts, unrelated CAS tree or Docker socket. Use a nonprivileged sandbox/container on the workstation and the equivalent in-cluster; if the isolation mechanism is unavailable, parsing stops rather than falling back to the host. Bound CPU, memory, walltime, pages, output, archive members/uncompressed bytes/expansion ratio; reject traversal/symlink escape and XML external entities/DTD fetching. A proposed `tests/district-parser-isolation.test.ts` fixture injects sentinel provider/source secrets into the parent and proves that each parser child's environment and filesystem cannot access them, and that network/archive escape attempts fail. This is a required future acceptance test, not a demonstrated exploit or a test run here.

### 2.2 Queue and storage: Postgres + private content-addressed store

**Choice: Postgres from the workstation stage onward, not SQLite/Redis plus a later migration.** One local Postgres instance holds scheduling, source identities, dependencies, receipts and publication metadata. A private filesystem CAS holds large bytes, normalized text, parser outputs and private provider responses. Do not put PDFs into Postgres or adopt a graph database for this rebuild.

Proposed schema `migrations/001_district_jobs.sql`:

- `source_snapshots`, `representations`, `policy_decisions`, `artifacts`: source identity/version and content hashes remain separate. Identical bytes may have multiple municipalities, URLs and policy proofs.
- `jobs`, `job_dependencies`, `step_receipts`: `job_key UNIQUE`, state, lane, priority, `not_before`, lease owner/expiry/fencing token, attempt number, input/output hashes and cancellation state.
- `host_lanes`, `provider_budgets`: shared admission capacity and reservations, not per-process best-effort counters.
- `case_identities`, `entity_identities`, `identity_assertions`: accepted/contested/retracted identity decisions with provenance and versions.
- `release_candidates`, `release_files`, `active_release`: manifest-bound immutable candidates and a small atomic active pointer.

Workstation CAS layout: private `cache/districts/cas/sha256/<first-two-hex>/<hash>`; no source bytes under public `out/`. Write a temporary object, hash and fsync it, then atomic rename before committing its receipt. An interrupted write may leave a collectable orphan, never a committed reference to an incomplete object. Object type/MIME live in metadata, not filename assumptions. Keep admitted originals private only as long as rights/retention allow; public releases contain facts, attribution and short quotes, never republished copies.

R1 establishes this schema, CAS and a **single-process bounded CLI executor**. R2 uses the same job/receipt contract for evaluations and batch waves. R3 completes the durable multiworker scheduler, crash recovery, scheduled increments and replay; it does not invent a different job format. R1/R2 may execute a preauthorized bounded batch without continuous owner attention, but must safely pause on an unresolved exception, budget/lease/isolation failure or expired authorization, recording an explicit resumable disposition and notifying the owner. They are not unattended production services before R3 recovery gates pass. Travel or an absent owner is never implicit permission to continue, switch models or publish.

R3 claiming uses a short Postgres transaction with `FOR UPDATE SKIP LOCKED`; workers execute outside the transaction, renew leases, then commit results only with the current fencing token. Dependencies release only after committed predecessor receipts. Delivery is **at least once**; uniqueness plus fencing gives single accepted effects, not magical exactly-once HTTP/provider calls. Record provider submission intent and returned request/batch ID. An ambiguous timeout is reconciled or held before paid resubmission; retries must not silently double-spend.

Later in-cluster: run the **same worker image and job types**, Postgres with persistent storage, and an S3-compatible private object store under identical content keys. Only scheduling/configuration and the CAS I/O implementation change. Set explicit CPU/OCR/provider concurrency; no cluster deployment is part of this plan's execution. Back up the database and referenced CAS together; a database-only backup is insufficient for replay.

### 2.3 Idempotency, invalidation and replay identity

Canonical JSON uses sorted keys, fixed numeric/date encodings and deterministic array ordering where order is not meaningful. Store a canonicalization version. Suggested key:

`job_key = SHA256(step + semantic_contract_hash + canonical(input_artifact_hashes, source_scope, selector, relevant_policy_proof))`

Specific identities:

| Kind | Identity / behavior |
| --- | --- |
| Discovery/fetch | Publisher + source ID + normalized resource identity + tenant/body/municipal scope + request selector/body hash + scheduled observation window. Do not strip meaningful query parameters or council tenant IDs. Validators and final URL are recorded, not treated as content identity. |
| Content/preparation | Bytes hash + parser/OCR versions, options and language packs. Byte-level work can be reused, while admissibility and municipality-specific claims remain separately scoped. |
| Triage/evidence | Text/structured artifact hash + candidate-generator version + ordered candidate IDs + calibrated classifier/model/prompt contract + scope. Candidate order affects choices and is part of the key. |
| Extraction/judge | Exact request hash + provider/model identity + schema/prompt/decoding contract; judge additionally binds candidate and generator-response hashes. No “latest” model alias without recording returned identity. |
| Linking | Sorted admitted mention/identifier evidence hashes + municipality/issuer scope + resolver/rule/calibration version. A renamed label must not renumber a verified native identity. |
| Publication | Sorted admitted fact/identity/coverage hashes **plus all non-knowledge staging inputs**, output schema, publication-policy snapshot, pinned graph `asOf`, and authentic **predecessor release/change-state hashes**. Bind `priorRelease.gitCommit`, `manifestSha256`, `releaseId`, and each prior city's `signals.geojson`/`changes.json`. Same complete inputs produce identical content files and manifest ID; wall-clock job receipts are separate. |

A current policy check is mandatory even on a semantic cache hit. If policy evidence changes without affecting permissibility or extraction semantics, create a new admissibility receipt referencing the unchanged original response; **do not relabel its generation provenance**. A changed gate reruns gates/linking/publication, not automatically extraction. A parser/OCR change invalidates text-dependent results, not the original fetch. Logging changes do not invalidate semantic work. Corrections/tombstones trigger only dependent records and graph edges; disappearance from a partial page is not deletion.

Preserve the existing `publish.ts`/`replay-pipeline.ts` **`priorRelease` contract**. City `changes.json` is computed against the earlier city's signals, or copied from the predecessor when signals are unchanged; knowledge artifacts alone cannot determine it. Publication dependencies/receipts therefore include the authenticated earlier manifest and its member hashes, catalogue, city signals/feeds, regional topics, core facts/manifests/handover inputs, quality inputs and all other required staging artifacts. Enumerate these from the pinned publisher's required-file contract. Missing predecessor state fails closed; never substitute the target release, mutable current output or an invented empty predecessor. An initial release needs an explicitly versioned genesis contract, not an implicit fallback.

Two replay modes are explicit:

1. **Exact offline replay:** pin registry/catalog/policy snapshot, source/CAS artifacts, model responses, versions, source evaluation time and graph `asOf`, **all knowledge and non-knowledge staging inputs, and the authentic earlier `priorRelease` manifest/member/change-state hashes**. Network and providers are disabled. Reconstruct every manifest-bound member, including city change files, and the identical manifest ID. Preserve original clocks inside hashed artifacts; new execution timing lives only in run receipts. Fixtures must show that the same current signals with different predecessors can yield different change files, unchanged signals retain authentic prior change state, and missing/target-as-predecessor input is rejected.
2. **Recompute:** intentionally change parser/model/gate/resolver and emit a new run/manifest plus semantic diff. Model regeneration is not guaranteed bitwise reproducible, even at deterministic-looking settings. A revoked source can be audited under retention rules but cannot be newly published by replaying old permission.

### 2.4 Per-host politeness and owner policy

The **owner's current policy supersedes stricter historical robots handling in the catalog/performance report**:

- Observe and record robots.txt but apply the explicit global owner override. Never misrecord `Disallow` as `allowed`; store observation and override separately. This override does not override authentication, CAPTCHA, paywalls, opt-out, third-party rights or provider terms.
- Process qualifying official works under §5 UrhG with document-level issuer/work evidence. This is not “everything on a government domain is official.” Exclude third-party works on reserved hosts; unresolved origin or rights stays held.
- Facts and short source quotes only. Public metadata is not a grant to republish original documents or personal data. Preserve current no-contact/no-private-person constraints; the top-15 council adapter initially publishes bodies/meetings/decisions, not a newly expanded people database.
- Use one honest versioned UA, e.g. `StadtstackData/<version> (+<owner-controlled-info-url>; contact=<owner-contact>)`; values must be real and supplied before any future fetch. Do not impersonate a browser or an unrelated research institution.
- Opt-out is checked at discovery, fetch, processing and release. An opt-out cancels queued work, invalidates affected derived artifacts and schedules removal from active public releases. Account for every managed raw/text/prepared/response/staging root and shared-content reference; hash dedup cannot bypass exclusion or leave an unaccounted copy. Record physical disposition versus logical exclusion, including backup-retention restrictions. Do not delete another authorized source's shared object blindly.

Use a **shared Postgres host lane**, keyed by normalized host and an explicit shared-service grouping where several hostnames represent the same portal. Never one independent limiter per municipality. All redirects acquire the destination lane and undergo policy checks. Wicket/other anonymous public session state is tenant-bound; sessions are not credentials to bypass access controls.

[INFERENCE] Initial conservative settings: one in-flight request per host, at least two seconds between request starts, maximum four independently eligible hosts at once; any stricter configured delay or `Retry-After` wins. A permitted host may later receive a measured higher limit, never automatically to hit a throughput target. Fair round-robin turns prevent a deep archive monopolizing a shared portal. 429/503 receive bounded scheduled backoff; 401/403/CAPTCHA/opt-out stop the relevant lane for resolution. Unknown provider quota is not recorded as healthy. Any explicit owner-watched subscription-quota mode must remain visible, bounded and stoppable; native quota/auth errors stop work.

### 2.5 Observability and accounting

Every attempt and cache hit emits a `StepReceipt` in `district-step-receipt.ts`:

- `runId`, `jobKey`, step/lane/source/municipality, attempt, lease token, category `production|evaluation|development`, dependency receipt IDs;
- enqueue/start/finish timestamps, queue wait, monotonic elapsed time, CPU time where measurable; retry/hold outcome and controlled reason codes;
- input/output hashes, policy/origin proof, parser/tool/schema/gate/calibration versions, cache disposition and original generation receipt;
- provider, endpoint, requested/returned model, request/response IDs and hashes, standard/cache-write/cache-read/output token categories, batch ID/custom ID;
- `actualBilledUsd` only if known, separately `estimatedApiUsd`, currency, rate-card date/hash, reserved spend and subscription usage availability. Missing usage/cost is `null`, not zero;
- bytes/pages/OCR pages/rows/spans/candidates, accepted/held facts and distinct cases; no secret headers, private paths, raw PII or document contents in public metrics.

Report p50/p95 execution and queue latency by step/host/provider; cold and warm preparation separately; CPU, wall-clock interval union and provider wait separately. Track recalls and false finalization, policy holds, source completeness, case-chain completeness, identity disputes, cache reuse, cost per changed group and per useful answer. Do not add overlapping step walltimes into “project duration,” treat CLI API-price estimates as invoices, or count repeated copies as independent evidence. Extend existing `district-model-usage.ts` rather than creating a competing cost ledger.

### 4.4 Evidence is a choice, not generated quotation text

`district-evidence.ts` deterministically segments immutable text into paragraphs/sentences, dates, amounts and table cells. Each text span binds `textSha256`, page/section, UTF-16 `[start,end)` and ID; cell evidence binds row/column/native record and header semantics. A change of OCR/parser creates a new span space. Do not normalize quotes after selection in a way that changes the source.

The model selects **IDs and typed roles**; code reconstructs exact quotes and numeric/date values. Both decision APIs in the supplied report allow at most 255 choices: reserve `none`, `missing`, `uncertain`, leaving **252 actual candidates**. Multi-evidence selection uses independent predicates or repeated choice with a `stop` convention replacing an appropriate sentinel, never 256 options. Long documents use section selection then span selection, or bounded exhaustive candidate waves; measure losses at both stages. Truncated context must be explicit and route onward, not quietly become `irrelevant`.

Ask separately about topic, case, legal/action stage, date role, number/unit/financial role and actor/relation direction. Nearby words do not prove a relation. Select a contiguous statement with both actors and predicate or a structured relation justified by named source fields/schema. For Jev, put the question's actual meaning in instructions/state/criteria; the request key alone is not model context. Respect its reported 64k total and 32k state-plus-longest-question limits; revalidate limits before use.

Choice construction guarantees only literal reconstruction. It does **not** prove that an objection was accepted, that a quoted actor is the operator, or that a planned amount was paid. Uncertain, conflicting, multi-case or poor-OCR selections go to residual extraction with sufficient original context. Until a new verification contract is independently evaluated, model-derived claims retain the existing deterministic gates and actual faithfulness judging (current threshold **0.8**, critical unsupported claims fail); never synthesize a historical judge score. Same-model judgment remains explicitly not independent verification.

## 5. Case identity and entity resolution

### 5.1 Keep four layers separate

1. **Representation:** one URL/fetch/version; mirrors are not corroboration.
2. **Source content:** exact bytes/text; one gazette may describe many cases.
3. **Case/project and events:** the enduring undertaking/procedure plus versioned decisions, permits, awards, payments and results. One project may have several procedures/lots; do not merge all into a single event.
4. **Actors/programmes/assets:** the actual organization, funding-period programme, facility or energy unit, with evidence-based identity links.

The current `district-schema.ts` has case types `diplan`, `bobsh`, `paper_reference`, `plan_number`, `source_document`; current graph identity is identifier-set/name/scoped grouping and explicitly **not legal-entity verification**. The rebuild must preserve that distinction. In particular, a `source_document` key is a fallback mention bucket, not a counted project. The performance report's repeated Schulcampus records demonstrate why record count must not become project count.

### 5.2 Deterministic identity rules

| Object | Strong canonical key / rule | What does not establish identity |
| --- | --- | --- |
| Municipality/authority | Verified AGS/ARS + identity/boundary history; authority/body native ID scoped by issuer/tenant | Five-digit district prefix as a town ID; shared Amt host as a shared municipal government |
| Plan/procedure | Publisher namespace + native DiPlan/BOB/UVP/WFS identifier; otherwise issuing municipality + plan type + exact plan number + explicit amendment/version | Same plan number across towns; geometry overlap or generic “2. Änderung” alone |
| Council event | Issuer/tenant/body + native paper/resolution ID and documented year/version; event ID distinct from project ID | Similar title, same meeting, or committee agenda date as actual final adoption |
| Organization | Verified identifier tuple `(namespace, issuer, value)` such as MaStR actor ID or registry court+register type+number; preserve legal form and validity interval | Name alone, domain, postcode, address, parent-group membership or shared brand |
| Programme/operation | Managing authority + fund/programme code + funding period; operation/FKZ ID scoped by issuer | “EFRE,” “Kommunalrichtlinie” or similar programme titles without period/authority |
| Procurement | Native procedure/notice ID + notice version; lots and awards separately keyed; TED/federal equivalence only from explicit cross-reference/ID semantics | Similar project description or contract title as a cross-source equality |
| Financial measure | Municipality/issuer + fiscal product/investment ID + applicable plan version; payments keyed separately with period/scope | Same amount, generic “Schulbau,” budget total, award price or a programme-level sum |

Normalize whitespace/Unicode and documented ID formatting for comparison while retaining original values. Preserve legal forms; transliterations and abbreviations are candidate aliases, not merge authority. An exact strong identifier can group renamed mentions when issuer/type/time are compatible and there is no contradictory identifier; store aliases rather than putting the label into the durable identity key. Conflicting strong identifiers always block auto-merge. A person/contact-free source-scoped mention remains valid even when no canonical entity can be established.

Cross-document linking first uses explicit native references. Example: a budget investment ID explicitly printed in the council decision links those events; a shared FKZ links a funded operation; a permit file reference links a decision and conditions. Only after that use candidate blocking by AGS/authority, topic/object class, normalized distinctive name, temporal compatibility and geography. Geometry/name/year similarity is never sufficient to manufacture `same_as`, `operates`, `funds` or a payout.

Merges are versioned identity assertions with evidence, rule/model version, author/adjudicator and status `accepted|proposed|contested|retracted`. They are reversible; keep original mentions and source IDs. Before a transitive union, check the whole proposed cluster for incompatible identifiers/types/periods—A≈B and B≈C do not automatically establish A=C. Corporate succession is a dated relation, not erasure of distinct legal entities.

### 5.3 Decision-model assistance

`district-entity-resolution.ts` generates bounded candidate pairs in code. Decisions/Jev/Haiku choose `same_identity`, `different_identity`, `related_not_same`, or `insufficient_evidence`, and select the supporting evidence IDs. Use separate tasks for **entity identity** and **case-event attachment**; topic similarity is not either label. The model cannot invent a registry identifier or retrieve private data.

Start model-assisted matches in shadow mode. Assessment pairs include same-name town utilities, GmbH versus GmbH & Co. KG, facility versus operator, amendments, duplicate notices, programme periods and changed legal entities. Use §4.1's blind A/B, deterministic reconciliation and third-pass protocol, with unresolved cases and sampled audit only for the owner; distinguish provisional consensus from independently validated pairs. Report pair precision/recall **and cluster false-merge/split rates**, qualified by label provenance. Hard conflicting IDs override any model choice. Cross-municipality legal-identity merges require a strong shared identifier or explicit authoritative identity evidence plus this review protocol; model probability alone is never enough. Accepted reviewed decisions are pinned artifacts for replay, not hidden manual edits to graph JSON.

### 5.4 Graph publication and value

Build only from admitted evidence plus admitted identity assertions; extend the existing graph byte binding to bind both input sets in the manifest. Keep planned/conditional/negated/historical relations visible with their actual modality but excluded from confirmed-current paths unless the query explicitly requests them. The graph must not infer “not funded” from no edge.

**Temporal admission is required in addition to modality.** Extend graph/identity schemas and `district-graph-query.ts` with evidence-backed effective intervals for ongoing operator, membership, programme and identity assertions: normalized `validFrom`, `validTo`, boundary inclusivity/date precision, the original temporal expression and supporting evidence. Distinguish unknown bounds from expressly open-ended applicability; `null` must not mean “valid forever.” Keep `observedAt`/`retrievedAt` separate from legal/operational validity. Pin a release `asOf` in publication identity and query receipts; an explicit query override is also returned and cache-keyed, never read implicitly from the wall clock.

A **current/as-of path** requires every ongoing relation and every identity assertion used by the path to be supported at the same `asOf`; their effective intervals must overlap there and contain no unresolved contradictory/superseding evidence. An ended operator relationship is excluded after its end, and edges from disjoint periods cannot form a contemporaneous shared-operator path. A dated statement with unknown present validity is returned only as an attributed historical/as-observed claim, not a confirmed-current edge; absence of an end date or a recent fetch does not prove continued operation. Broader historical searches retain explicit intervals and qualification.

Financial/legal events instead keep their **own sourced event dates and chronological roles**: a 2023 approval and 2025 payment can legitimately form a case chain without simultaneous event dates. Verify entity identity and the relevant role at each event time; distinguish “ever supported by the same programme” from contemporaneous programme participation. Proposed fixtures cover expired operators, disjoint intervals, unknown validity, corrections/successions, fixed-as-of replay and valid non-simultaneous approval→payment chains. Update path filters, MCP input/output descriptions and caches together; the existing type/modality predicate alone is insufficient.

Publication yields `knowledge/records.json`, `knowledge/graph.json`, `knowledge/coverage.json` and the existing release manifest, with a proposed separately bound `knowledge/identity.json` if identity assertions cannot fit cleanly in records. Update `data-release.ts` path allowlist, mandatory file bindings, graph validators, MCP readers and tests together; no unbound sidecar or compatibility shim. Existing immutable historical releases retain their schema/provenance; the new live contract is a clean cutover.

For cross-town queries show the precise shared entity/programme identity basis, source-backed edges, dates, conditions and gaps. Keep statistical/derived observations and uncertain candidate links distinguishable from direct assertions. A result chain does not imply causation without an appropriate study/design; link a measured outcome as an observation with its methodological limitations.

**Why R1's ≥30/60 is appropriate but not guaranteed.** The enhanced run gained only eight usefulness points despite much larger extraction, while seven graph questions gained none. To justify a rebuild, source-native operator/programme/permit identities and finance/resolution joins must do substantially more: **18 additional usefulness points over 12/60**, with at least eight full practical answers, is a meaningful go/no-go test. The top-15 sources plausibly address governance, planning, operator, award and financial-chain questions; they do **not** guarantee measured outcomes or the same programme across the exact named towns. The score is deliberately a value hurdle, not a count of records, implemented adapters or successful abstentions. If the relevant facts are inaccessible, keep the result honest and revisit the product decision.

**Why R2 aims for 34 rather than 60.** Better span/date/role selection and residual extraction can recover a few additional answers from already targeted evidence, but cannot create an absent annual account or outcome study. The four-point gain is a proposed quality hurdle; token savings alone are not a substitute. **R3 holds 34**, because durability should preserve value rather than “discover” it by changing the rubric.

**Execution sequencing:** after the shared adapter/evidence/job contracts are pinned, independent source adapters and assessment-data preparation can run concurrently; scheduler hardening can proceed against those contracts without waiting for every source. Cheap GENESIS/context work runs alongside, not ahead of, the council/funding/permit/finance chains. Gauges/GTFS/atlas breadth remains in R1 as specified; reducing it requires explicit owner scope approval, not an implicit “fast path.”

## 8. Implementation hand-off and non-goals

The first implementation ticket should pin the settled acquisition/release commit and registry/catalog snapshots, then add the R1 structured-evidence/job contracts and licensed native-ID adapters. Reuse existing `district-document.ts`, `district-prepared-document.ts`, `district-answer-cache.ts`, gate/schema modules and manifest-last publication; migrate their callers rather than maintaining a second pilot pipeline. The current model provenance accepts subscription providers only, source types are limited, and graph/schema predicates are narrower than this plan: all must be deliberately extended, with no fake CLI/provider/judge identity for API or structured records.

At the end of each future implementation phase, the integration owner should run the repository's type/build/test checks plus the new adapter/policy/identity/span/batch/replay fixtures and the frozen value evaluation described above. Those are **proposed checks, not executed results in this planning task**. Candidate release checks must bind the exact image digest/version, `serverInfo.version`, `get_release_status.release.version`, and `release.dataManifestId == dataManifest.id`; deploy only under the existing release approval process. Rebuild phase labels do not assert which semver is live.

Non-goals: agent orchestration in production, new crawls or paid experiments during planning, legal identity inferred from names, missing-source “zero” claims, corpus republication, a graph-database migration, real-time guarantees, autonomous expansion, or changing the 30-question test until the system looks successful. The product outcome remains **more complete, correctly qualified, source-backed answers at lower repeat-processing cost**.
