# R2 scale design: incremental municipal generations

**Status: design only.** No source fetch, model call, production-state write, migration, extraction, seal, release or deployment is authorized here. This design preserves the existing evidence, policy, assessment, custody, quality and security gates. Estimates are explicitly **[INFERENCE]**; they are scenarios, not observed capacity or promises.

## Executive decision

**R2 now (only if it fits without delaying the currently gated R2):** freeze exact semantic-contract hashes separately from host/custody runtime hashes, and add content-addressed reuse at the artifact boundaries for *future eligible work*. Do not reuse R1 extraction/assessment outputs for the current R2 semantic change. R2's extraction design changes context spans, date roles and relation semantics, so R1 evidence remains historical; its 208 originals still require fresh R2 preparation/extraction/assessment under the changed contract (`R2_EXTRACTION_DESIGN.md:3,7-12,67-73`; `R2_FOUNDATION_DESIGN.md:206-211`). The no-delay option is first a design/interface slice: exact contract identity and artifact-key schema, with no alteration to live worker scheduling or inventory cutover. If implementation cannot be reviewed and landed as a small isolated change, defer its code to immediately after R2; never change R2's approved work sequence or bypass gates to claim reuse.

**Immediately after R2:** establish partitioned inventory and source-level incremental seal/replay/publication; then onboard municipalities through a generated registry and reviewed source-policy/owner approval workflow. Per-municipality growth must append only that municipality's changed artifacts and update the bounded global indexes/manifest, not load/rewrite/revalidate the entire corpus on every ordinary operation. The global objection/purge path remains authoritative and cross-partition.

The design target is $W=O(D_{new}+D_{changed}+S_{changed}+P_{changed})$ per campaign, where $D$ is documents, $S$ source scopes requiring re-seal and $P$ changed publication members. A strictly global administrative objection/purge is necessarily proportional to the affected host's cross-partition postings, not one arbitrary partition; it must not silently become a corpus-wide scan.

## 1. Incremental generations and reuse identity

Each immutable generation manifest records exact source/registry/policy snapshots, input membership, semantic contracts, artifact references, publication membership and predecessor generation. It is a new generation, never an in-place relabeling of receipts. A prepared output, extraction, assessment, seal, or publication member is reusable only when its complete typed key and original committed receipt validate:

`K = (originalSha256, municipalityId, sourceId, semanticContractId, sourcePolicyValidityId, relevant model/tool identity, artifact kind/version)`.

The semantic contract identity is a canonical digest over only the stage's meaning-changing inputs (prompt, output schema, parser output contract where parser bytes are semantic input, extraction/projection logic, model route/configuration where it changes output). Each stage's key additionally pins exact parent artifact hashes: extraction pins prepared text/manifest; assessment pins the exact extraction target and rubric/assessment contract; seal pins the exact source membership and all relevant stage receipts; publication pins exact member bytes and provenance. No title, URL, timestamp, mtime, similarity, mutable “latest” alias, or source-wide cache key is sufficient.

`sourcePolicyValidityId` is a separately authenticated, source/job/permission scoped policy proof and validity interval, not a timeless “allowed” bit. Reuse is prohibited if an applicable permission expires, policy/robots/TDM state changes or becomes stale under its rules, owner override changes, source is withdrawn/objectioned, original bytes differ, authority epoch invalidates the proof, or any prerequisite receipt fails. Reuse re-checks current rights/policy and objections; it does not repeat model or parser work when those checks pass. A negative/hold is reusable only under its exact frozen inputs and contract and remains a hold, not admission.

Never relabel or regenerate a historic receipt to a newer generation/contract. The new generation records a reference to the original artifact and receipt identities, their original generation, and a fresh validation receipt asserting eligibility under the new generation. Reused assessments retain their original model and review receipts; they are not described as new A/B/C calls or new independent reviews. If a semantic contract changed, affected artifacts are recomputed and all required assessment gates receive fresh receipts; unrelated artifacts can remain byte-identical and referenced by their real original lineage.

### Replay and step-8 validation of reuse

R2's current full-reextract choice avoids stale historical replay, and the current replay implementation assumes today's source contracts must equal the archived generation (`R2_EXTRACTION_DESIGN.md:12`; `replay-pipeline.ts:214-216` and `:271-313`). Incremental generations must instead authenticate a typed DAG:

1. Ordinary delta commits authenticate the generation root and follow only changed document/artifact paths, changed source-policy scopes and affected revocation postings. They do **not** read or validate every reused artifact or recompute the whole corpus closure. Keep authenticated persistent membership/dependency indexes keyed by exact artifact, parent, source, host, contract and policy identities. Each index node/subtree carries a Merkle hash and validation proof for its exact children, schema/version, membership and ancestry; the committed root authenticates these roots and the predecessor. A delta validates changed leaves and their ancestor paths, plus every policy/revocation scope it touches, then atomically updates affected paths and root. Reused subtrees are accepted by verifying their pinned authenticated subtree roots/proofs and absence of relevant invalidation/revocation, not by trusting an unverified cache or caller-supplied index.
2. Before a reuse reference is committed, validate the artifact bytes and original receipt against the exact historical contract archive, source/policy/authority ancestry, exact source SHA and parser/preparation ancestry. This is needed for a newly touched artifact or when its scope is invalidated; unchanged authenticated subtree members are not rescanned on every ordinary delta.
3. Recompute only stage projections whose relevant semantic dependency, parent artifact or required policy validity changed. A changed prompt/schema/extractor invalidates its dependent stage closure; changed infrastructure/security code causes current security/runtime proof validation but not semantic re-extraction unless it changes the semantic output contract.
4. For each newly reused/touched item, emit a fresh *validation/reference* record pinning historical receipt IDs/hashes, historical contract archive hash, current eligibility checks and new generation. This is not a replacement receipt and cannot rewrite history.
5. Replay changed public members from authenticated inputs; for unchanged members, authenticate the pinned prior-generation subtree/member hashes and validation ancestry. Check exact path membership via the authenticated membership-index proof. Persist an ordered changed-member byte comparison and unchanged-member pinned hash/length rows, each with binding-set hash. Any mismatch, absent membership proof, invalidation or changed attribution fails closed.
6. Ordinary step-8 delta validation covers the complete frozen-campaign membership/accounting through authenticated membership/dependency proofs, validates changed and invalidated members plus affected source seals, dispositions, assessment ancestry and current objection/purge state. It must not regenerate or scan the full corpus closure. An explicitly authorised **full independent audit** is a separate operation that traverses every member/subtree, re-reads pinned bytes and independently rebuilds the entire closure; it produces an audit receipt and is not part of ordinary delta cost.

No “full replay” escape hatch is required for unchanged members: their immutable bytes and complete membership are authenticated by pinned hash proofs and Merkle/DAG ancestry. A changed release-wide manifest is reconstructed from authenticated full membership-index roots; only members that differ need to be regenerated. Preserve canonical byte replay for changed members and never repair a mismatch by copying the candidate over the regenerated result. A full independent audit remains available under explicit authorization, with cost proportional to the full corpus.

## 2. Semantic contract granularity and security binding

Today the step-8 set has 14 families (`r1-step8-current-policy.ts:90-100`). The mixed closures bind orchestration, IO, policy/security runtime and semantic output logic together. `district-claims.ts:194-198` explicitly fingerprints 13 extractor files; `district-prepared-document.ts:97-100` hashes preparation modules plus parser-output contract; `district-residual-jobs.ts:41-44` combines extraction with residual job/inference/cache/model code. Parser output and parser-isolation identities are already distinct (`district-parser-isolation.ts:62-89`), a pattern to extend. `R2_FOUNDATION_DESIGN.md:174-202` records the full 14-family sensitivity scan: a marker touching only `civic-opt-out.ts`, `district-r1.ts`, `polite-fetch.ts` changes acquisition, parserIsolation and ompRunner (3/14), while the broader scan changes 13/14. These are simulated sensitivities, not final hashes.

Split each contract family into two explicit pins:

- **Semantic output contract**: prompt + prompt version, schema and parser-output bytes/format, pure parser/mapping/extraction/projection logic, relevant canonicalization, model route/configuration when it affects content. This is the digest in the reuse key.
- **Execution/security contract**: isolated runner/container/image/tools, credential resolver, network policy, limits, filesystem boundary, custody/IO implementation, durable receipt protocol, authority/objection implementation and host runtime. This is checked against current approved security policy at execution and replay, but its hash alone does not invalidate already authenticated semantic output.

A security fix remains bound by receipt ancestry: every execution receipt pins the exact security/runtime contract, image/tool identity, authorization/review and source-job binding used at the time. Current replay checks that the historical receipt was valid under its then-authorized security contract and that its evidence has not been revoked; a separate current security gate confirms the artifact is safe to consume and has no outstanding vulnerability/withdrawal action. A fix that changes what bytes are admitted, parsed, exposed to a model, or which output can be produced is *not* “infrastructure only”: it changes the semantic input/output contract and invalidates affected outputs. If a security advisory requires invalidating old artifacts, issue a scoped revocation/recompute decision, not a global accidental closure hash change.

## 3. Partitioned custody on log-structured v2

Use **generation partitions** (foundation Option 2) as the physical unit, with municipality/source partition IDs in every document/artifact reference. Municipality/source partitions improve locality and ownership; immutable generation segments group deltas and avoid requiring 319 individual inventory files. Each committed generation delta contains only new/changed records and explicit membership/state transitions. Persist authenticated per-partition membership/dependency indexes mapping exact artifact, parent, source, host, contract and policy identities; index nodes carry Merkle hashes/proofs for exact membership and ancestry. A small authenticated root manifest commits to segment chain, partition index roots, global reverse-index root and predecessor generation hash. Read/write validates only touched partition paths and ancestor paths, not the entire historical log; a pinned subtree proof authenticates unchanged contents without rereading them. Compaction is bounded to a partition and produces a new authenticated checkpoint while retaining prior immutable history as required.

The existing log-structured v2 inventory direction and strict precommit capacity checks remain prerequisites (`R2_FOUNDATION_DESIGN.md:7-12,145-155`). Partitioning is not permission to weaken exact-set binding, objection epochs, safe-file identity, fsync, capacity accounting or membership tombstones. Partition writes are serialized under the existing lock/authority transaction, publish the new segment before atomic root-manifest replacement and recover fail-closed. Bound partition segment/index sizes and reject before commit if projected partition, root manifest, global index or hydrated memory exceeds limits. Ordinary operations cost `O(changed partition paths + touched global-index paths)`; they do not hydrate or validate all partitions.

**Global objections and purge:** objections are recorded durably before any inventory/index load or purge lock, exactly as now. Maintain an authenticated host→partition/artifact membership reverse index and source→partition index, with epoch and exact binding validation. A global host objection walks only that host's postings, verifies each target's immutable bytes/provenance and updates affected membership states/tombstones across partitions. Purge acknowledgements cover every affected CAS path and lease; if index integrity is unavailable, objection remains durable and processing fails closed while a separately bounded forensic scan/remediation is performed. Never allow an index miss to authorize reuse or to claim a purge complete. If one host legitimately spans many municipalities, purge cost is proportional to that host's affected postings; ordinary non-objection work remains partition-local.

## 4. Per-source incremental seals

A source seal is a deterministic manifest over source identity/policy, exact source document set and original SHAs, relevant preparation/extraction/assessment receipts, dispositions, registry/permission proofs and custody closure. Keep every seal immutable. For each source compare exact prior membership and per-member artifact keys. If no inputs, policy validity, registry binding, semantic contracts or relevant receipts changed, authenticate the prior seal and emit a new-generation reference/validation receipt; do not rebuild the full closure or relabel the old seal. If k documents changed, recompute only their affected work and update the source manifest delta. Full current policy/objection and membership validation still occurs before issuing a new seal reference.

Seal independent sources concurrently under bounded source-level workers, respecting the 8-CPU/16-GB machine, source-owned sandbox isolation, DB/authority locks and per-source rate/access limits. Parallelize CPU-bound preparation/closure work within explicit memory ceilings; never share a source-bound sandbox, policy permission, credentials or mutable fetcher across sources. A source with a changed registry, policy, semantic contract, permission or global objection revalidates the affected scope; it does not automatically force all other sources to reseal. Expected source seal effort becomes proportional to changed members/closure delta plus the current validation pass, rather than repeating the observed 1–3 hours/source for all sources.

## 5. Incremental publication and replay

Represent publication as an ordered immutable member table `(path, sha256, byteLength, schema/contract, exact source binding set, generation)`. On a delta, rebuild changed members and dependency-affected members only; keep unchanged bytes in CAS and preserve their original receipts/lineage. Reconstruct the release manifest from the full exact member table (small bounded metadata operation), not by regenerating every member. The manifest and public API must expose a coherent single generation, never mixed unauthenticated revisions.

For ordinary delta commits, authenticate unchanged members/subtrees from their pinned Merkle roots, membership proofs and established byte-validation ancestry; do not reread unchanged contents. The prior byte hashes/lengths were verified when their immutable subtree was admitted, and the authenticated ancestry plus proof that no relevant dependency, policy or revocation scope changed establishes reuse eligibility. Changed members are read, regenerated and compared byte-for-byte/length against their candidate; worker-supplied hashes alone are insufficient. Verify the complete exact path set and no extras through authenticated membership-index proofs, with schema/canonical encoding, source attribution, provenance, current policy and assessment gates separately bound. Record changed-member byte comparisons and unchanged-member subtree/member hash proofs in one ordered aggregate replay audit. A separately authorised **full independent audit** traverses every subtree, rereads every pinned byte sequence and independently verifies hashes, membership, provenance and full closure; ordinary commits do not perform this corpus-wide reread.

A source-policy change can alter publication eligibility without changing extracted text; regenerate affected publication/provenance/manifest members and reevaluate exclusions. An assessment-contract or extraction-semantic change invalidates every dependent record/member, not unrelated records. Revocation/purge masks are applied before serving and in replay proof; publication incrementality never makes a withdrawn record visible.

## 6. Municipality onboarding pipeline

Automatable steps, all proposal-only until owner authorization:

1. Generate a candidate municipal registry entry from the authoritative municipality catalogue (AGS, official names/aliases, district, locality relationship), with stable IDs, canonical source scope, registry schema/code/config hash and explicit `proposed` status. Validate no duplicate/ambiguous identity and exact municipality/source mapping. Preserve distinction between municipal catalogue coverage and actual evidence coverage.
2. Discover source candidates from official municipality/district sites, council portals, gazettes and registered structured catalogues. Crawl only within an explicitly bounded candidate plan; produce URL/host/source proposals, document types, source ownership evidence, robots/TDM observations, terms/licence and access notes, and provenance. Discovery can identify candidates, not authorize fetch or admission.
3. Run automated robots and TDM checks, terms/licence parsing where supported, origin/access checks, TLS/redirect/domain checks, document MIME/size/URL and crawl-limit checks. Capture source-bound policy receipts with exact observation time/URL/response hashes and explicit `allowed`, `disallowed`, `unknown`, authentication/access barrier or review-needed states. No inferred permission from neighboring towns or similar portals. Unknown/ambiguous policy is a hold.
4. Produce a batched owner-review packet, grouped by municipality and source owner, with registry diff, exact root/domain scope, discovered source list, policy/rights receipts, candidate document count/size, purpose/topic, risks, requested access/collection ceiling, model lanes/subscription plan and expiry. Owner decision cryptographically/otherwise authentically binds exact packet hash, scope and limits; batch approval can cover multiple sources only when each binding is enumerated. Changes to scope require a new decision.
5. After approval, materialize the frozen acquisition manifest; recheck current policy and authority immediately before each operation; collect bounded documents, deduplicate exact original bytes only within valid source identity, and issue immutable receipts. Run staged sample and owner quality review before scaling. Registry update and published evidence coverage remain distinct.

**Owner-required:** legal/policy interpretation where automated terms/TDM parsing is uncertain; approval of new source/domain/municipality scope, collection ceilings, policy overrides, model lanes and any paid expenditure; source-specific access credentials/agreements; resolution of blocked/authenticated sources and ambiguous authority; approval of manual identity/alias decisions; review of source quote/quality sample and release. No automated registry generator, crawler or policy parser may self-approve its own proposed scope or turn a robots/TDM refusal into permission.

## 7. Capacity model (planning scenarios)

For a comparable planning density, use **36.5 documents/municipality [INFERENCE]**, the midpoint of the cited R1/R2 planning range of about 34–39 docs/town (`R1_STATUS.md:148`; `R2_PLAN.md:3,36`). Totals are therefore ~1,825 at 50 municipalities, ~10,950 at 300 and ~11,644 at 319 registered municipalities. This is not a claim that each registered town has evidence coverage. The prior 48-doc scenario would be a deliberate +31.5% uplift over the 36.5 midpoint, not the baseline; it is excluded here to avoid silently overstating density.

Model calls are derived separately by stage: `extraction calls = sum(selected extraction chunks)`, `judge calls = judge-eligible extraction candidates`, and `assessment calls = A + B + C calls for each assessed item`. In the simple successful case of one extraction chunk, one judge-eligible candidate and one assessment item per document, this is **at least 5 calls/document** (1 extraction + 1 judge + 3 assessment), not 3. Holds before a model call reduce calls for held documents; post-extraction/assessment holds may incur some or all of these calls. Multi-chunk documents, multiple judge candidates, C reconciliation and authorized retries increase the count. A/B/C use remains subject to its separate approval and lane controls.

CPU per document uses the weak one-document R1 extraction proxy 5.45 CPU minutes plus 4–10 CPU minutes policy refresh, total 9.45–15.45 CPU min/doc **[INFERENCE]**, excluding preparation, seal, publication, queue waits, assessment CPU and retries (`R2_FOUNDATION_DESIGN.md:213`; `R2_PLAN.md:74-83`). Wall time uses 8 CPUs idealized where noted; model/service latency and seal seriality dominate actual wall time. Inventory size uses a minimal one-record/document 0.88–1.10 KB proxy based on historical inventory bytes, not measured v2; actual inventory includes many receipts/proofs/leases and is estimated separately below (`R2_FOUNDATION_DESIGN.md:91`).
