# R2 foundation design — Vikunja #105

**Status:** design only; based on `33fa1d3`, on branch `r2-foundation-design`. Owner decision C closes R1 without a step-8/9 execution or data release and starts R2 Medium (100–140 targeted documents). This document authorizes no source fetch, paid API/model call, production-state write, migration, release or deployment. R2 must use new consumed namespaces and its own authorized generation; failed R1 generation names and receipts remain immutable history.

## Decisions

1. Use a strict, versioned, content-addressed Core codec: immutable proof atoms → exact binding-set hashes → per-path artifact references. Set equality is exact canonical equality, never similarity or subset matching. Host/source reverse indexes are committed and authenticated with the same inventory epoch.
2. Migrate the existing inventory only after the separate, governed retirement of the failed step-8 roots and a full old-reader drain. Never deploy a live v1/v2 dual-writer or an ignored sidecar/WAL.
3. Pin assessment originals, using the core idea in unmerged `34e3cbf` with integration and tests; do not copy CAS payloads or the source-wide proof union onto each item/A/B/C artifact.
4. Replay every candidate output and manifest byte-for-byte, but persist one aggregate replay proof/audit and the exact inputs needed to independently rerun. Candidate bytes are already committed; do not persist a second replay copy of them.
5. Make Core capacity validation a pre-commit invariant and add an exact whole-step8 + step9 capacity pre-pass. Preserve the 500,000 logical-record cap and 480 MiB per-file `MAX_STATE`; do not raise either to mask expansion.
6. Keep R1's already-merged same-source sandbox batching and safe lifecycle coalescing. Add only job-bound, permission-scoped reuse for robots/TDM state; never reuse a fetcher or permission result globally.
7. Keep R1 documents and receipts immutable. Where R1 source evidence is reused by R2, use its historical pins; perform a seal-only renewal only if current policy/expiry or changed source membership requires it. Do not re-extract solely because Core storage changed.
8. **Ontology:** no domain concept, relationship, lifecycle or civic assertion changes. This is internal custody/persistence representation, so neither `docs/ontology.yaml` nor `docs/ONTOLOGY.md` needs an update.

**Rejected alternatives**

| Alternative | Decision |
|---|---|
| Raise the limit to 750,000 or 1,000,000 | Reject: the measured/frozen step-8 forecast at 750,000 leaves only 10,395 for an unmeasured step 9; a larger cap conceals record amplification and leaves no demonstrated headroom. |
| Copy assessment originals and persist a full replay-output copy plus one audit envelope per member | Reject: pin-original's forecast removes 256,416 copy entries; replay output/envelopes account for another 183,530. Hash-pinning originals and comparing regenerated bytes preserves evidence with less mutable duplicate custody. |
| Merge registry families, HTTP admissions, or independent/source flags to improve deduplication | Reject: it changes exact-set semantics and can convert a non-independent source into an apparent independent one. |
| Keep a live old-reader compatibility mode, v1 sidecar or dual-write during cutover | Reject: stale readers/writers can commit incomplete provenance and crash recovery becomes ambiguous; drain, atomic version swap, old-reader fail-closed. |
| Share a process-global fetcher/policy cache or re-extract all 208 R1 documents on a new codec | Reject: the first violates source/permission/expiry boundaries; the second changes historical lineage without an extraction-semantic reason. Reuse immutable pins and renew seals only when required. |

### Exact representation and preservation rules

Use three immutable, explicitly versioned record types in Core's sealed inventory segments:

- **Proof atom:** the complete canonical provenance identity, keyed by hash of the versioned canonical encoding. It retains `kind`, canonical host and URL digest, source hash/nullability, observation and receipt hashes, retained-publication or git-snapshot proof fields, registry configuration/schema/code/approval family, and `independentAllowed`. It is immutable; `active/revoked/deleted/missing` state belongs to each artifact/path reference, not to the globally shared atom.
- **Binding set:** the sorted unique proof-atom hashes for one exact proof closure, keyed by a versioned hash. Do not sort away fields or deduplicate by source hash alone. An artifact reference pins one `bindingSetSha256`.
- **Artifact reference:** the current root ID, path, content digest, lifecycle state and binding-set hash. It remains distinct per path/root/content; sharing the proof set never merges artifacts or authorizes access.

Scratch leases use the same atom/set codec while preserving their exact purpose, phase, owner, directory identity, groups, daemon resources and tombstones. The codec change does not archive or discard leases. The binding-set codec version and canonicalization version are explicit in the physical manifest and each segment; unknown versions fail closed.

Exact-set constraints:

- Registry families remain distinct unless the existing Core's complete-equivalent-family rule proves the full configuration and endpoint digest set identical. The set codec itself does not normalize them, merge partial families, or infer an endpoint.
- Every HTTP admission remains represented. Different URL hashes, redirect/observation IDs, receipt hashes, source hashes or independence flags yield different proof atoms even if the content bytes match.
- `independentAllowed` is part of proof identity. Raw/independent HTTP selection continues to require the exact independent binding; an artifact's larger set does not confer independent status on a member.
- No set lookup skips `assertHostNotOptedOut`, authority/epoch validation, file digest checks, exact declared-vs-actual provenance comparison or the existing purging behavior in `civic-opt-out.ts:1161–1218,1623–1674`.

A reverse index contains canonical host → artifact references/live leases, source hash → references, and host+source → references/sets. Its serialized hash, record count and inventory epoch are pinned in the same committed manifest/segment chain. Every load validates the codec/hash and validates index membership against the authenticated reference/atom tables; a caller-supplied or stale index cannot authorize anything. Index updates and artifact state transitions are one locked transaction. A missing or inconsistent bucket is `inventory unavailable`/incomplete and blocks read, objection, purge or revocation; it never falls back to “no matches.” Live host objections remain uncached and are checked at each existing boundary. The reverse index only accelerates complete discovery of affected references.

### Migration and old-reader cutover

1. Obtain the separate owner/operator authorization for overflow retirement, preserve all failed-generation claims/receipts and record actual retirement receipts. Require a fresh census proving the post-retirement count and exact inventory/authority hashes; 256,228 remains a forecast until then.
2. Freeze/drain all inventory writers and readers that can retain mutable snapshots, including 0.3.2, old R1 tools and active scratch/daemon callbacks. Resolve live/partial leases under the existing recovery procedure first. Confirm no independent Core consumer remains running. Old 0.3.2 is not a compatible rollback reader for every current resource variant; top-level v1 readability alone is insufficient.
3. Under the existing shared inventory lock, record old inventory/authority/segment hashes and build a new v2 staging generation from the exact old logical view. Validate every root, entry, source proof, scratch record, lifecycle state and tombstone; compare expanded old and compressed new views exactly, including host/source reverse-index equivalence and binding-set negative cases. Preserve all records other than the separately retired roots.
4. Fsync new segments and their directory before preparing the new manifest. The manifest authenticates the codec version, complete segment chain, inventory identity, indexes and prior generation hash. The old inventory remains authoritative until an atomic manifest swap; write an authenticated migration intent/checkpoint with explicit `prepared`/`committed` phases. Crash before swap → old inventory remains authoritative and staged files are ignored. Crash after swap → new manifest hash is authoritative and startup validates it. Any unknown/mismatched hashes, partial chain, missing index or ambiguous phase fails closed; never guess or concatenate old and new generations.
5. Release the lock only after the v2 committed manifest is durable. Old code must reject the new strict schema/codec; do not leave a v1 materialization or live WAL that old writers can use. Keep the byte-identical old inventory backup read-only for the reviewed rollback window. Rollback is allowed only before v2 writes and only by atomically restoring its exact checkpoint; after any v2 mutation, recovery is forward-only through v2.
6. Update every Core consumer and operator handoff before deployment. A cutover is not permitted while any old process might write from a stale in-memory inventory. The migration run itself is authorized evidence with real hashes/clocks, not a fabricated receipt.

## 2. Pin-first evidence and canonical replay

### Assessment originals and `34e3cbf`

**Decision: adapt, do not blindly cherry-pick, `34e3cbf` (`r1-step8-pin-original`).** It is unmerged, unverified and no tests ran. Its three-file change adds `pinOriginalStep8Assessments`, removes the per-role byte-copy budgets and uses `createReadOnlyManagedSourceAudit` to hash-check original CAS paths. This is the right direction: the forensic assessment forecast has 121 bundles × four roles (484 copies), 586 source-union bindings per source and **256,416** copied Core entries; the first original item/A/B/C CAS blobs each had one `prepared_source` binding, while the copied role used 546. Preserve each original's own source closure, not the 546-binding union sprayed onto every copy.

Adapt the patch by making the CAS manifest pin `(assessmentId, municipality, source, role, original path, original hash)` and by authenticating each original using the new Core source-audit/read API with one fresh authority/inventory/objection epoch. The path must remain the exact immutable CAS path and hash; do not copy bytes, rewrite old assessments, infer a missing ID, merge source identities or permit symlink/path substitution. Fail closed on original mismatch, duplicate assessment identity, changed binding set, stale/changed epoch or host objection. The existing audit in-memory capability must not escape its managed lifetime. `r1-step8.ts`, step-8 assessment loader/acceptance, Ops handoff and step-9 ingestion must consume the same pin manifest. No old copied handoff shape is silently upgraded.

### Replay and one audit representation

The replay contract is unchanged: regenerate all **46** outputs in `replayPublicOutputs`, regenerate the release manifest, and compare canonical bytes/byte lengths for every required public member and manifest against the candidate. No hash-only shortcut replaces byte comparison. The public snapshot lists 45 manifest members plus the manifest and README as 47 persisted files; independently authenticate the README/operator artifact as a pinned input even though the forecast's 46 replay outputs are the compared public outputs. If a candidate manifest/member differs, fail the replay/gate; do not repair the candidate or copy the mismatch to a new path.

Persist one versioned aggregate replay proof/audit with ordered rows for every output path, candidate hash/length, regenerated hash/length, equality result, exact binding-set hash, and all runtime/source/contract/input pins needed for a clean independent rerun. The audit hash covers the entire ordered table and manifest comparison. Do not persist replay output copies or one source-bound audit envelope per output. On a later independent check, rebuild from pinned candidate inputs and recompute every row; the compact audit is evidence of the comparison, not a replay cache or permission.

The loader, `r1-release-acceptance.ts`, Ops gate/handoff (`scripts/r1-step8*` and `docs/R1_STEP8_OPERATOR.md`) and step-9 consumer (`evaluate-pilot-value.ts`/candidate evaluator) migrate together: each validates the versioned Core codec and the single aggregate audit, exact candidate membership, existing assessment pins, source bindings, current objections and receipt ancestry. Public release member bytes, source attribution and the frozen question/denominator semantics do not change. The step-9 path reads the accepted candidate and its audit; it cannot require discarded duplicate replay payloads or accept a handoff merely because its JSON parses.

## 3. Pre-commit capacity and step-9 reserve

`saveInventory` must project the **complete next logical inventory before publishing any segment**: current hot rows + cold rows + all new rows/atoms/sets + state deltas + scratch leases + root/index changes, deduplicated by the exact new Core identity. Reject before new segment publication, hot-manifest replacement or any externally visible commit if any bound would be exceeded. Preserve the existing lock, strict schema validation, safe-file identity/digest checks, atomic replacement and fsync. Orphan segment recovery remains fail-closed; a capacity rejection is not a partial commit.

The high-level read-only pre-pass runs before expensive reconstruction and again under the execution epoch, using the same pure projection and versioned Core identity code as the writer. It enumerates **every root and every phase**: staging, candidate/assessment manifest, public snapshot, input/provenance, replay receipt/audit, final proof/handoff/gate and the full step-9 output set. It calculates per-phase and peak union, exact duplicate atoms/sets/refs, entry-state changes, lease deltas, every encoded writer's byte limit and worst transaction/cache peak. The execution path recomputes before each commit; a new writer family without a pre-pass bound is refused. Capacity forecasting never predicts permission or source access.

Hard gates:

- Keep Core `MAX_INVENTORY_RECORDS=500,000`; count all live logical artifacts/proofs/sets/leases across hot+cold, never only the currently serialized manifest. The proof-set representation changes the unit being counted but does not drop tombstones or history.
- Keep `MAX_STATE=480 MiB` per existing physical file. Additionally impose a proposed **768 MiB aggregate hydrated-wire ceiling** over the complete projected manifest, all live segments, proof sets and reverse indexes. Before commit, compute exact next-generation serialized bytes and a deterministic `hydratedUpperBound`: type-specific worst-case decoded record/index allocations (from canonical field lengths and posting counts), simultaneously resident old and projected snapshots, and the largest serialization/read/transaction buffers. Pin the estimator coefficients to the codec/runtime contract and calibrate them against maximum-shape fixtures; if a runtime/schema adds an unbudgeted allocation it must fail closed until recertified. Proposed acceptance is `hydratedUpperBound ≤2 GiB` and measured process RSS ≤2 GiB, with no more than 75% of either limit used by the full step8+step9 fixture. These are new design thresholds, not existing measurements.
- Provisional planning floor: reserve **at least 75,000 logical records [INFERENCE]** for step 9 and uncertainty until the exact step-9 writer projection is measured. Set final reserve to `max(75,000, ceil(1.25 × measured complete step-9 peak delta))`. Do not start step 8 unless the entire measured step-8 maximum plus this reserve is **≤450,000**, leaving at least 50,000 records of real headroom to the 500,000 Core limit. For illustration only, the fan-out-only 371,592 plus 75,000 is 446,592 and leaves 53,408; exact codec/index overhead can make this fail. If the measured step-9 reserve exceeds 78,408 with this step-8 estimate, or actual v2 overhead pushes the sum above 450,000, reduce amplification further and remeasure—do not steal reserve or raise the cap.

Tests must prove that the historical 500,040 boundary is rejected *before* a segment/manifest commit, including when overflow is cold, and that a within-cap multi-root hot+cold save/reload preserves exact identities, objections and recovery semantics. Capacity failure cannot mutate authority, CAS, roots or publication state.

## 5. Processing-contract transition and R1 evidence policy

There are 14 named processing-contract families in `contracts-baseline.json`: preparation extractor, residual preparation, residual job, joint extraction, assessment queue, assessment B, acquisition, policy refresh, structured-state-gauges (adapter/parser/mapping/semantic), operator registry, parser output, parser isolation, OMP output and OMP runner. The earlier fresh-process simulation in `R2-INVENTORY-NOTES.md` §3 changed only `civic-opt-out.ts` bytes and found exactly two changed fingerprints: `parserIsolation` (`287e701c… → 27d66d0c…`) and `ompRunner` (`95265109… → ebfb1170…`); the other twelve were byte-identical. Those were sensitivity hashes for the simulated 500,000→750,000 edit, not new approval pins.

For this design the intended processing-source change set is `civic-opt-out.ts` (codec/capacity), plus `district-r1.ts`/`polite-fetch.ts` and a new explicitly hashed policy-cache module if job-bound reuse is implemented. The fresh-process, in-memory `readFile`-only contract simulation is to be recorded in this design commit; it must show the actual current fingerprints changed by that file set, with exact baseline and simulated values. Expected closure is **parser isolation and OMP runner** from `civic-opt-out.ts`, plus **acquisition** when its handler/fetcher/cache changes; the OMP output contract intentionally excludes Core custody. The step-8 pin/audit/acceptance files are not processing-contract inputs, so no processing fingerprint changes merely because their audit wire changes. The final implemented tree must rerun all 14 fingerprints in fresh processes using readFile-only substitutions before any new hashes are pinned. Simulation hashes are impact evidence only, never a release, parser-review or runner authorization.

Transition window:

1. Keep R1 receipts, seals, parser/runner pins and source contracts immutable. Do not edit or relabel R1 DB/CAS receipts to look like R2.
2. Before R2's new source jobs, freeze and review the exact changed-file set, compute actual final contract hashes, obtain the appropriate security review/review-file updates for parser isolation and OMP runner, and include the new job-policy module in the acquisition contract closure. Direct B's current-generation contract must bind the actual new runner pin. Old code/old hashes remain historical; no mixed code/receipt alias.
3. Schedule cutover as a no-writer window: stop/drain all old Core users and callbacks, complete the authenticated v2 migration, then start only the reviewed compatible Core and new R2 worker. Old readers fail closed after the strict codec swap. Record real timestamps, hashes and migration/review receipts. If any old process cannot be proven stopped, do not swap.
4. Keep the new R2 corpus/generation separate from R1. The 100–140 R2 documents are deduplicated against the 208 frozen R1 documents by exact municipality/source/original identity, not title or URL alone. R1 pins can be carried as immutable retained evidence under their historical contracts; they are not rerun to manufacture a new receipt.

**Seal/re-extraction decision:** do not re-extract R1's 208 documents solely to change the inventory codec or contract fingerprint. If an R2 candidate actually consumes one of the 27 R1 source seals, reuse its immutable source/extraction/assessment lineage and require a genuine **seal-only reauthentication/renewal** only where its manifest/source membership changed or the current-policy validity horizon fails the step-8 window. A seal-only renewal creates new authentic seal/current-policy evidence but does not rerun extraction or overwrite R1 results. If no R1 output is selected into R2, no R1 reseal is needed. Re-extraction is required only for changed source bytes, a real parser/extraction semantic change that R2 elects to adopt, or an unbindable historical result—not for storage refactoring.

Cost evidence: R1 observed source seals at **1–3 hours/source** (`R2_PLAN.md` §3 / `R1_STATUS.md`); renewing all 27, if required, would be **27–81 source-hours [INFERENCE]**, not an authorization or calendar promise. R1's stated 4–10 CPU minutes/document gives **13.9–34.7 CPU hours [INFERENCE]** to re-extract all 208, before preparation, assessment, retries and seal work. That cost and unnecessary new model evidence are avoided by the seal-only choice. Current SS-01 stop means neither renewal nor re-extraction is executable now.

## 6. Ontology

The R2 implementation must continue to represent original source, independence, assessment and replay states without adding a new user-visible civic concept. No ontology edits are proposed.
