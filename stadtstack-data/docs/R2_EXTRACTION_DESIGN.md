## Decisions

1. **Add same-original context spans, not broader arbitrary chunks.** Preparation will emit a versioned context-span manifest for bounded cover/header/footer/signature and instrument-specific procedural spans, all bound to the same admitted original SHA-256 and prepared-text SHA-256, offsets, span hash, role and case/instrument identity. A chunk references zero or more such spans; these remain separate from its contiguous chunk text. Prompt input names each span and its role. Every quote carries a locator to exactly one source span; deterministic quote validation checks the exact substring there, and checks original/text/context hashes and offsets. Never synthesize a quote by concatenating chunk and context, borrow from another case in a gazette, infer physical PDF page numbers lost during preparation, or allow context to override the chunk's case. The signed/bound source remains the admitted original; context only enlarges the audited evidence selection from that original.
2. **Split document and event dates.** Replace ambiguous date extraction with `documentDate`/`documentDateQuote`/reason and event-specific `stageDate`/`stageDateQuote`/reason; retain historical `stages[].date` and its event-bound quote. The document-date quote may resolve against a permitted context span. A stage/decision quote must bind to the event wording itself, not just a document header. A historical procedural event never populates the current stage/adoption date. A single year or month/year is **not publishable precision in R2**: retain it only as an explicitly typed `datePrecision` value within an evidence/candidate record, and keep it non-publishable until its role can be represented and downstream consumers support that precision. For the first R2 cut, simplest is explicit `datePrecision: day | month | year`, with publication-date eligibility requiring `day`; non-day is an explicit hold. No guessed day/month or date normalization that manufactures one. This records truthful precision without relaxing the existing date gate.
3. **Decouple relation admission from record-date promotion.** Keep the R1 rule that a released knowledge record needs a sourced full date (document, stage or historical event), and keep exact one-span relation quotes/endpoints. A relation itself does **not** need an independent date quote merely to be a graph assertion: the admitting record's dated source establishes the observation/document context, while relation time remains optional and is required when the claim is historical/temporal under existing modality semantics. If the enclosing record has no acceptable date, do not release that record to the dated knowledge-record feed; instead permit a separately assessed, source-attributed relation contribution only when its own exact quote, both entity mentions, explicit predicate, modality, source/document identity and required temporal qualifier pass all existing graph deterministic and review gates. It must not inherit a guessed date, turn a plan into action, imply current validity, or bypass source/identity/assessment/revocation policy. Existing `graphIdentityInputs` consumes admitted record relations and graph edges inherit text evidence/source hashes (`district-graph.ts:47–59,72–165,190–224`); create an explicit relation-admission projection consumed there, rather than silently admitting all relations from a held record. The graph's source time may remain unknown/role-aware; no relation event date is synthesized from record fetch time. The relation may only appear in an eligible path according to `relationPathEligible` (`district-graph-claims.ts:163–169`).
4. **Reconcile the 34 never-prepared entries through governed dispositions and real parser paths.** Never silently drop frozen corpus members or treat ancillary text as native preparation. Recompute exact original identity, import disposition, seal/source policy and terminal reason. The 24 stale import rejections require a fresh, explicit current owner-authorized import-disposition decision bound to the selected native seal/corpus, exact source/document IDs, original SHA/bytes, reason code and scope; authenticate it through the existing `authenticateImportDispositions`/current-decision path (`r1-step8-import-dispositions.ts:22–110`, `r1-step8-import-disposition-contract.ts`) before preparing anything. Do not relabel rejected entries as accepted by editing a prior receipt. Resolve the other 10 via their actual terminal exception/disposition: retry only where a documented recoverable prerequisite is now satisfied; retain permanent/unsafe/duplicate exclusions as exclusions. No blanket reopen. Add bounded, isolated, receipt-bound parser support for admitted ZIP and HTML inputs: ZIP must safely enumerate/select supported text-bearing members with limits and reject traversal, symlinks, encrypted/unsupported entries, expansion bombs and ambiguous member selection; HTML must extract visible text with scripts/styles excluded while preserving source mapping sufficiently for exact quote binding. The current preparation tool version routing includes ZIP→`python3`, other non-PDF→`node` (`district-prepared-document.ts:86–94`), but this is not evidence that ZIP is supported end-to-end. Keep parser isolation and parser output contracts independently versioned and reviewed; unsupported content remains a visible hold, never fallback to ancillary raw projection.
5. **Rebind every changed processing contract.** Context manifest fields change `district-prepared-document.ts`/`district-schema.ts`, preparation output and `preparationSha256`; quote restoration schema/locators and `district-inference.ts` input assembly change; this is explicit input addition to the 13-source `EXTRACTOR_SOURCE_FILES` list and its ordered fingerprint (`district-claims.ts:194–198`). Revise jointly the extraction and judge prompts/schema (`district-claims.ts`, `district-inference.ts:28–31`): two date roles, named context-span locator, exact quotation from one declared span, historical event separation, and precision hold. Since the emitted wire schema changes, `CLAIM_SCHEMA_SHA256`, extractor hash, prompt/work-plan identity and answer-cache binding change; old cache/results cannot stand in for new semantics. Context-aware chunks must change extraction cache locators/binding (the current model receives only `source.text=chunk.text`, `district-inference.ts:123–136`). Any relation-only contribution schema/admission path changes graph claim/schema, `district-graph.ts`, publication inputs/composition, assessment target projection and graph/release contract dependencies; it must be authenticated end-to-end. Residual jobs bind preparation + joint extraction + separate residual output hash (`district-residual-jobs.ts:41–44`), so their output assembly/locator/contract must change when they accept context spans or relation projections. Assessment dependencies and item quote locators must include context-source pins and relation evidence; old A/B/C decisions do not assess new claims. Parser output-contract hash changes for ZIP/HTML parser implementation, and parser isolation/security review pins change if worker/image/tools/list changes. Update every schema consumer/projection/query/release serializer; no compatibility alias or silent stripping.
6. **R1 re-extraction decision: a bounded sample is required for measurement; re-extract all 208 is not required.** R2 needs fresh extraction evidence for the 10-document context/date and relation measurement sample because the semantics and source payload change; run it only after a separate owner-authorized sample, with subscription-lane receipts, source/job/group IDs, model/tool identity, usage/allowance records, and immutable cached answers/work-plan/contract archive. The 10-doc run is not a publication authorization. Do not re-extract every R1 document merely to adopt the new contract: old R1 lineage stays immutable. A full R1 re-extraction is warranted only if R2 explicitly wants re-evaluated outputs from those R1 originals; then all 208 results are a new generation, not an in-place update, with model cost, receipts, assessment and publication replay. For the first sample, select 10 exact admitted R1 originals spanning boundary-context positives (including Ludwigslust and Hoppegarten/Strausberg where applicable), Hagenow already-in-chunk date controls, at least one relation-rich source, and parser/import categories only if the selected 10 actually include them; stratify and publish the sample selection before calls. No R1 paid-call/cost claim is implied.

## Contract and execution boundary

- **Preparation/context:** version the manifest and span locator; include manifest bytes/format in `preparationSha256` and prepared receipt. Revalidate all span hashes, offsets, normalized text mapping, source SHA, original bounds, case association and parser receipt at each use. Do not use retrieval time, filename dates, or unadmitted OCR/raw projections.
- **Extractor fingerprint (13 explicit files):** adding context metadata to schema/prepared-document and quote-restoration requires updating the explicit ordered producer source file list, not relying on transitively changed code. `district-claims.ts:194–198` computes SHA-256 from `{version, hashes}` across those 13 files. Update the fingerprint/version and receipts; archive actual sources. `district-inference.ts:28–31` binds extractor + both prompts into the joint extraction contract; schema SHA remains a separate identity. A prompt-only edit changes prompt identity; schema changes change schema hash; inference/input assembly changes extractor identity.
- **Residual:** `district-residual-jobs.ts:41–44` binds preparation, joint extraction and a separate output hash over residual job/inference/cache/model modules. Add the actual context/relation projection consumer to its output closure and bump the output contract. No silently stale residual item or offset.
- **Assessment:** A/B/C assessment item quote locators, original-source pins and critical graph propositions must bind context span hashes/offsets and each relation contribution. Assessment queue/dependency hash changes, prior assessments are not transferable. R1 judge/A/B/C evidence remains immutable; fresh R2 evidence and receipts are required for changed claims.
- **Re-extraction economics:** no full 208-doc rerun just to change hashes. For any actually reused R1 source, preserve old extraction and assessment lineage; perform only a new seal/current-policy renewal if policy expiry or source-membership change requires it. A sample extraction is a new authorized model generation under subscription lane(s), with metered usage/allowance and authentic model/tool/cache/response/work-plan/assessment receipts. A full 208 rerun, if separately chosen, entails **13.9–34.7 CPU hours [INFERENCE]** at analysis planning’s 4–10 CPU min/document, before preparation, assessment, retry and sealing, and cannot be hidden as “rebind” (`R2_FOUNDATION_DESIGN.md:160–162`; not an authorization).
- **ZIP/HTML contract:** preparation parser output hash and, for shared worker/image/tool-list changes, parser-isolation review hash must change; receipt records actual parser/image/tools and output hash. `district-prepared-document.ts:86–94` shows parser output contract and tool selection; `district-parser-worker.py:11–19,69–90` shows fixed sandboxed tools and request boundary. Do not execute HTML/ZIP support in a less isolated host process. No new parser test or output contract is accepted without behavioral boundary tests and security review.
- **Knowledge publication and graph:** define relation-only admission schema, its exact source evidence, record-to-relation provenance edge, relation assessment binding, revocation masking and build/validate projection. It must be included in release composition/dependency hashes and public projection where applicable. Existing `knowledgePublicationHold` remains strict for records (`district-publication.ts:102–110`); it may not infer a relation date from a record. Relation time is optional only for non-temporal assertions where existing graph semantics permit; historical relation requires explicit time, and graph path eligibility remains exactly modality-sensitive (`district-graph-claims.ts:163–196`).

## Test slices — behavioural tests only

All future Node/TypeScript tests/typechecks obey the supplied `flock … taskset -c 2-7 nice -n 10` CPU rule. No wording tests, string-presence tests, import-only checks or relaxed schema assertions.

1. **Prepared context and exact quote binding:** hashed same-original cover/signature context resolves an exact date quote; one-byte source, context-text hash, offset, wrong source, adjacent unrelated gazette case, quote spanning concatenated chunk/context, and stale prepared receipt all fail. UTF-16/normalization mapping uses real accented/surrogate examples. Confirm retrieval/file dates are rejected as evidence.
2. **Date roles/precision:** historical event date cannot populate current stage/adoption; header date can populate document date but not a stage event; month/year and year remain held and never become day; wrong-case signature cannot be selected; Hagenow in-chunk full document dates pass document role while event/adoption remains unknown unless independently quoted.
3. **Relation independently held:** date-held source record remains absent from dated-record publication while an exactly quoted, assessed relation is included in graph under its own provenance; relation evidence still fails for missing endpoint/predicate, altered quote, missing historical time, invalid modality, revoked source, failed assessment or unadmitted identity. A document date alone cannot make a relation historical/current; removal of source record removes its relation contribution absent its own binding.
4. **27-row trace and survival:** replay the sealed R1 native rows/artifacts and assert every one is classified to exactly one authenticated terminal reason; 14 native quarantine candidates cannot be promoted without passing their actual failed checks; 11 missing contribution rows get exact admission reason; two final date holds separate record and relation disposition; no double count after graph projection/identity dedupe.
5. **Never-prepared workflow:** import disposition rejects stale/expired/mismatched seal, source, document or bytes; no import without current owner decision; terminal exceptions remain exclusions unless documented retry condition is satisfied. ZIP traversal, symlink, encrypted member, over-limit expansion, ambiguous text member and HTML script/style text are rejected/excluded; supported visible HTML and selected ZIP member retain exact locators and receipt hashes.
6. **Contract invalidation:** behaviorally prove old preparation/cache/answer/assessment/residual bindings cannot be reused under changed context or schema; new work plan and contract archive validate only with exact changed source/prompt/schema/output hashes; old R1 receipts continue validating against their recorded old contract. Avoid tests that merely assert a hash string changed.

## Evidence limitations

The checked-out R1 package at base `33fa1d3` does not contain `docs/ontology.yaml` or `docs/ONTOLOGY.md`; attempts to read both at the package docs path found no such files. Therefore this design makes no claim of a user-visible ontology change. Its relation-time choice is grounded in the existing admitted graph schema/temporal projection and modality gates (`district-graph.ts:47–59`, `district-graph-claims.ts:163–196`): a relation can have no explicit event time where its semantics permit, but historical relations require quoted time; observation/document provenance is separate. Before implementation, the owner must supply/identify the canonical ontology artifacts and review this as a no-new-ontology-concept projection; do not silently invent ontology terms. Source evidence reviewed includes `district-graph-claims.ts`, `district-graph.ts`, `district-publication.ts`, `district-r1-step8-export-projection.ts`, `district-prepared-document.ts`, `district-claims.ts`, `district-inference.ts`, `district-residual-jobs.ts`, `r1-step8-import-dispositions.ts`, `district-parser-worker.py`, and the pinned analysis JSON. No tests/builds/model calls/fetches were run for this design.
