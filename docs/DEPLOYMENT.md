# Deployment

How to run Ledger of Life somewhere other than the owner's laptop. Test networks only; nothing here moves real money. Where a step was not run, it says so.

## The image

`Dockerfile` builds one image that serves the web app (`node server.js`) and runs the reconcile job (`node scripts/reconcile.mjs`). It holds code and the published city data (`stadtstack-data/out`, 94 MB). It holds **no** keys, database, env files or contract artifacts: `.dockerignore` is deny-by-default, and the image was checked for them.

```bash
docker build -t ledger-of-life \
  --build-arg NEXT_PUBLIC_PRIVY_APP_ID=<public Privy app id> \
  --build-arg NEXT_PUBLIC_PRIVY_CLIENT_ID=<public Privy app client id, optional> \
  --build-arg APP_ORIGIN=https://ledger.stadtstack.eu .
```

- `NEXT_PUBLIC_*` values are compiled into the browser bundle, so they are build arguments (`NEXT_PUBLIC_PRIVY_APP_ID`, and optionally `NEXT_PUBLIC_PRIVY_CLIENT_ID` and `NEXT_PUBLIC_SOLANA_DEVNET_RPC_URL`). A malformed Privy ID fails the build at prerender, which is the intended failure.
- `APP_ORIGIN` is also a build argument, only because prerendered pages carry absolute link-preview URLs; without it their preview image points at localhost. It stays in the build stage. The running server still reads `APP_ORIGIN` from its own environment.
- The base image and the Dockerfile syntax are pinned by digest (Node 24.21.0, resolved on 30 September), so a moved tag cannot change what builds and runs the image. The Dockerfile says how to update the pin.
- Privy: on 30 September the owner added `https://ledger.stadtstack.eu` to the app's own Allowed Origins (Privy's wallet iframe now allows `http://localhost:4175` and `https://ledger.stadtstack.eu` as frame ancestors), so the hosted build needs no app client and `NEXT_PUBLIC_PRIVY_CLIENT_ID` stays empty. A client, with its own allowed origins and the same users, remains possible later. Privy has no API for app settings.
- `.github/workflows/image.yml` builds the hosted image: `linux/amd64`, pushed to `ghcr.io/giraeffleaeffle/ledger-of-life`, actions pinned to commit SHAs, and the job summary prints the digest to pin. It runs from the Actions tab once the file is on the default branch, or by pushing a tag `image-*` on a commit whose CI passed. It reads its public build values from repository variables (`NEXT_PUBLIC_PRIVY_APP_ID`, `APP_ORIGIN`). **First run on 30 September:** tag `image-20260930-92b952c`, about 6½ minutes on a cold cache, digest `sha256:49ebff60…7559`. The package is public: an anonymous pull by digest works. That exact image was run read-only on amd64 with all capabilities dropped: healthy, `/api/status` reports the store on the volume, the front page and `/welcome/strausberg` answer with link previews on `https://ledger.stadtstack.eu`, an unknown city answers 404, no server errors. **Second image, same day:** tag `image-20260930-6010e5c`, digest `sha256:6cbf8c0b…6193` (pinned in `deploy/values/ledger.stadtstack.eu.yaml`), CI green on that commit. Run the same way: `/api/status` reports `identity: true` with the app id compiled in, the Local-stakes manifest is at its path and the AI desk's payee resolves from it, every page carries the anti-framing headers, uid 1000, no errors.
- Build for the CPU of the nodes that will run it. The Hetzner nodes are `amd64`, and a `linux/amd64` image (`docker buildx build --platform linux/amd64`) was built in 144 s under emulation and run read-only with all capabilities dropped: healthy in 8 s, pages and the reconcile route answering, no errors. A `linux/arm64` image was also built and run.
- A build with a warm npm cache took about 25 s; the first build also downloads the dependencies. The image is 580 MB. The build uses `npm ci --ignore-scripts`, as CI does. The lockfile used to be missing two optional packages (`@emnapi/core`, `@emnapi/runtime`), which made `npm ci` fail on Linux, and so likely CI's install as well.
- **`npm run build` in the working tree works again (fixed 30 September).** Turbopack had stopped with "Symlink stadtstack-data/cache/venv-jev/bin/python … points out of the filesystem root": server modules that read files by a path chosen at run time made it scan the whole project, including the city-data pipeline's git-ignored Python virtualenv, which links outside it. Those path expressions now carry `/* turbopackIgnore: true */` (comments only, in 11 `src/server` modules; runtime behaviour and the env overrides are unchanged). Checked: a reproduction failed before and built after, a standalone build still starts and serves `/api/status`, and the real `npm run build` in the working tree passes. CI and the image were never affected.

- The server writes only to `/data`. `/app/.next/cache` exists so a read-only root filesystem starts cleanly; nothing needs to write there.
- `HOSTNAME` is forced to `0.0.0.0` by the start command. `server.js` binds to whatever `HOSTNAME` holds, and container runtimes normally set it to the container or pod name. It was confirmed that the server then answers from another container on the network; what Kubernetes sets was not observed.
- `GET /api/status` answers with `storeAvailable`. The image's health check fails when it is false. `SIGTERM` stops the server in about 0.25 s.
- Every response forbids framing by other sites (`Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY`) and sends `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin` (`next.config.ts`). Privy's wallet frame is Privy's own page inside the app, so it is not affected.
- With a named Docker volume, `/data` inherits the image's ownership. A Kubernetes volume needs `fsGroup: 1000`; `deploy/chart/templates/deployment.yaml` sets it, and the first release on the cluster proved it (the store opens and writes on the volume).
- **Site tUSDC faucet:** `POST /api/test-usdc` requires a signed-in account, same-origin request and verified Solana wallet. It mints to that wallet, not an address supplied by the browser. Default allowance is 10,000 tUSDC once per 24 hours per account **and** wallet, with 200 requests per UTC day globally. Persistent storage reserves the allowance and journals the signed mint before broadcast; retries recover the original request and signed transaction rather than minting again. Keep that storage durable across restarts and replicas. A `pending` response is not success; repeat the same endpoint to reconcile it. Missing configuration returns `unconfigured`, not a Circle-faucet fallback: Circle's token cannot fund a tUSDC tenancy. No deployment or mint transaction is implied by adding these settings.
- **Simulated deposit yield:** `POST /api/deposit-yield` accepts only `agreementId` and a stable `requestId`, never an amount or recipient. It requires the recorded tenant's verified Solana wallet and passkey. `releaseAllowed` permits claims after funding during the tenancy; otherwise finalized settlement is required. Recover a `pending` response with the same request ID shown by the journey's `simulatedYield.pendingRequestId`. Each tenancy has one durable in-flight claim, and confirmed payouts subtract from later yield. Exact signed bytes are journaled before broadcast; ambiguous RPC evidence does not justify a replacement. Keep these journals and finalized funding/settlement slot observations durable across replicas/restarts. Failed or provably expired transactions pay nothing; a new claim ID may then claim the still-owed amount. Faucet cooldown/quota do not limit yield, which is bounded by confirmed accrual less already claimed yield. No on-chain mint/deployment was exercised for this addition.

## The scheduler

Run `node scripts/reconcile.mjs` about once a minute (for example a Kubernetes `CronJob` from the same image) with `APP_ORIGIN` and `RECONCILE_SECRET`. The route checks the secret, not the origin, so `APP_ORIGIN` for the job may be the in-cluster address. It tries every scope, even when an earlier one fails, and exits non-zero only after all of them ran:

- `robinhood` and `solana`: reconcile pending operations against the chain; they answer `unconfigured` until the chain settings exist.
- `price`: copies a new Chainlink RHTSLA/USD round from Robinhood Chain mainnet into the testnet feed when every check passes (the Tesla token is not paused, the round is fresh, Jupiter's TSLAx price agrees within 5%, at least an hour since the last copy, within 20% of it); otherwise it skips and says why.
- `local-ai`: removes stored questions and answers after `LOCAL_AI_TEXT_GRACE_SECONDS` (600 by default) and truncates the SQLite write-ahead log. Both are needed: without them the removed text stays in the database file and the log (checked: 20 copies remained; with the fix, none). Postgres keeps dead rows until autovacuum, which this job does not force.
- `building-income`: prunes private node readings/totals to 30 days even when income is unconfigured. With a dedicated fee key, mints **simulated feed-in paid by this site**, a **lower bound of measured production**, to the pinned distributor. A node reports its energy-today counter's local date and IANA timezone; accepted signed observations are within five minutes of receipt. Day D requires at least three fresh observations during D and is settleable once a later-local-date reading arrives, or more than one hour passes after D's timezone-aware end (including DST). The highest observed energy-today value is the lower bound, not extrapolated full-day production; missing end-of-day samples do not invent energy. The first post-opt-in observation establishes the opt-in day's baseline; only later energy on that day qualifies. Later completed days use their full observed maximum. Each node/local day settles once, subject to the global UTC reservation-day cap. Pending signed journals recover unchanged even after readings age; unsigned journals require retained completed-day evidence and the same assignment or are cancelled without broadcast. `/api/status.buildingIncome` reports configuration, public signer and job health. This is not electricity-sale proceeds or a real-money payment; observations are device-reported, not independently verified.
- Solar reports are self-attested: the Ed25519 signature proves the enrolled node key, not a physical meter, ownership, audited yield or an electricity sale. Owner opt-in declares finite positive peak capacity in kWp (maximum 1,000) and starts `pending`; an allowlisted operator must approve it through `/api/home-node/approval`. Pending/rejected/paused assignments never authorize a new mint. Each node's physical-production ceiling is `min(declared kWp × 8 kWh/kWp/day, 100 kWh/day)`; any observed daily maximum above it persists an anomaly and pauses unsigned settlement for review. An operator cannot override an unresolved above-ceiling day. Correcting declared capacity requires renewed approval; the absolute 100 kWh/day ceiling remains. Operator enrollment is a manual authorization control, not independently verified production evidence.

## SQLite backups

The chart adds `ledger-of-life-backup`, every six hours at 00:00/06:00/12:00/18:00 UTC, using the same app image with a ConfigMap-mounted `node:sqlite` online-backup command. It reads `/data/rental.sqlite` (including committed WAL pages during concurrent writes) and writes to `/backups` on a separate **`ledger-backups`** 2 Gi ReadWriteOnce `hcloud-volumes` PVC. Required pod affinity keeps it on the web pod's node to share `ledger-data`; no web pod means no scheduled backup until one is available. The job is bounded to 300 seconds, forbids concurrency, has no retries and keeps one successful/two failed Job histories. It is non-root uid/gid 1000, fsGroup 1000, read-only root, drop ALL, RuntimeDefault, no service-account token or Secrets. Its `backup` label matches only the existing ingress/egress default deny; no network allowance is added.

Snapshots are mode-0600 `rental-<UTC timestamp>-<uuid>.sqlite` files. Before verification/publication, every `local-ai:request:*` record is scrubbed with the exact `purged()` field list from `src/server/local-ai-retention.ts`: empty `request.prompt`, null `request.answer`, and UTC `request.purgedAt`. The copy uses `secure_delete`, DELETE journal mode and `VACUUM`, removing old text from free pages, then must pass `PRAGMA integrity_check` before its `.partial` is published. Only after success are older snapshots removed: retain the **newest 28 successful snapshots**, about seven days at four successes/day (longer during failures). Interrupted partials are cleaned on the next run; they may not yet be scrubbed, so never restore or distribute them. Both data and backup claims are kept on Helm uninstall. Monitor backup Job logs and capacity: the backup PVC must hold 28 databases plus one in-progress copy and VACUUM temporary space; files are not compressed. **No off-site copy exists yet:** this protects against corruption and mistakes after a successful snapshot, not losing the whole cluster or all its volumes.

These are sensitive database copies **excluding desk questions/answers**: account identifiers, wallet addresses, chosen cities, tenancy/listing records, the AI host registry with public keys/invitation hashes, usage counters and signed transaction/payment journals. The reviewed hosted server flows keep API credentials and signing private keys in runtime Secrets, not the store; connector private keys stay on the host. A caveat from `src/server/adapters.ts`: local/explicitly enabled Home Assistant connections store a bearer token. Hosted configuration forbids new connections, but legacy/local records can still contain it, so there is no universal “secret-free database” guarantee. All desk text is scrubbed in the snapshot regardless of request age/state, including running/settling, without changing live text or its grace-period cleanup. Published backups therefore do not extend question/answer retention; restore retains usage/payment/workflow data but not former desk text. Never publish either volume or print record contents during inspection.

### Listing and restoring

Use the complete maintenance-Pod manifest and commands in [deploy/README.md — SQLite snapshots and restore](../deploy/README.md#sqlite-snapshots-and-restore). **Every inspection/restore step below needs the owner's separately authorised admin session:** the release wrapper only runs the existing `deploy/apply.sh` modes; it cannot scale, patch or exec a helper, and the filtered viewer is read-only.

1. Record the web pod's node and deployed image, then create the restricted `ledger-restore` helper from the runbook on that node, mounting `ledger-data` and read-only `ledger-backups`. Wait for Ready. List filenames without printing data:
   ```bash
   kubectl -n ledger-of-life exec ledger-restore -- node -e 'console.log(require("node:fs").readdirSync("/backups").filter(n => n.endsWith(".sqlite")).sort().join("\n"))'
   ```
   Delete the helper when done if only listing.
2. For restore, keep the helper; suspend the backup CronJob and wait for existing backup Jobs to terminate (suspending does not stop active Jobs). Ensure no backup Pod is Running or Pending.
3. Scale `deployment/ledger-of-life` to **0** and wait for all web Pods to terminate. No release or Secret replacement during this outage.
4. Select an exact `.sqlite` filename, never a `.partial`; re-open it with `node:sqlite` and require a single `ok` from `PRAGMA integrity_check`. With all writers stopped, copy it over **`/data/rental.sqlite`**, set 0600 and remove **`/data/rental.sqlite-wal`** and **`/data/rental.sqlite-shm`**. The runbook supplies the exact `kubectl exec` command. If copying fails, keep the web scaled down until a known-good snapshot is fully restored.
5. Delete the helper, scale web back to **1**, wait for rollout and verify `/api/status` reports `storeAvailable: true`. Review restored pending operations and host pairings, then unsuspend backups. Changes after the snapshot are lost; test-chain transactions, Privy accounts and external connector state are not rolled back.

Offline proof on 1 October: the current hosted values render 13 release objects plus two Helm-test Pods; all five workload pod specs meet restricted hardening, and the backup matches only default deny. The current pinned amd64 app image ran with a read-only root, uid 1000, all capabilities dropped and network disabled; `LocalStore` created a real WAL database with synthetic records while a second container ran the exact ConfigMap command. The snapshot passed integrity (`ok`), captured committed counter 1056 while the writer advanced to 1168, and had mode 0600. Retention kept the newest 28, an interrupted partial was cleaned, an unrelated file was preserved, a corrupt source failed without publishing/pruning, and restoring after stopping the writer recovered the exact snapshot counter. Temporary containers, volumes, pulled app image and smoke files were removed. Kubeconform is not installed here, so strict schema validation of this addition was not run. No cluster scheduling, volume attachment, live backup or cluster restore was exercised.

The privacy follow-up used the updated rendered command with four synthetic desk records in a real `LocalStore` (`completed`, `ready`, `running`, `settling`) while concurrent writes continued. Snapshot prompts were empty, answers null and purge timestamps set; state, ownership, usage and payment journals were preserved, integrity was `ok`, and live text was unchanged. Whole-file Node `Buffer.includes` checks confirmed both synthetic question/answer markers were absent from the published SQLite snapshot and present in the live database file. The grep tool returned no snapshot matches but also missed known binary matches in the live file; the whole-file byte checks supplied the decisive proof. Follow-up container, pulled image and temporary files were removed.

## Secrets and operator material

Supplied when the container runs, never built in, with three exceptions: the image contains the public manifests `contracts/evm/deployments/local-investments-46630.json` (Local stakes; the AI desk's payee), `contracts/evm/deployments/shared-market-46630.json` (the shared loan market and its price feed), and `contracts/evm/deployments/share-deposit-46630.json` (share-backed rental deposits), addresses, code hashes and parameters on Robinhood Chain testnet, because the app reads them at those paths. Rebuild the image when a deployment changes.

- Key files (`LOCAL_AI_FACILITATOR_KEY_FILE`, `ROBINHOOD_TEST_KEYS_DIR`, `SOLANA_TEST_SIGNER_DIR`). The fee-signer key must be owner-only (the code rejects any group or other permission bit) and readable by uid 1000. A plain Kubernetes Secret volume may not satisfy both; copying the file in an init container with mode 0600 is the likely answer. Not tried on a cluster.
- `contracts/evm/out` and the other deployment manifests, mounted under `/app/contracts/evm/`. Only the operator test tools need them; the hosted demo keeps those off.

## What a production build refuses by default

- **Home Assistant.** A production build never fetches an address a person entered unless `ALLOW_HOME_ASSISTANT_PULL=1`. Local setup sets it. On a shared host, leave it off: the address check cannot be relied on, because DNS is resolved again when the request is made.
- **Operator test tools.** Off unless `SOLANA_TEST_SIGNER_MODE=1` and `ALLOW_OPERATOR_TEST_ACTIONS=1`, and only without `DATABASE_URL`. They let server-held keys act for someone else: the landlord and arbitrator in Home, and the localhost earnings rehearsal's landlord. **The owner decided on 30 September that the public site runs real flows only**, so they stay off there and remain for rehearsals on localhost. The per-wallet market with a fake test stock and its price and yield levers no longer exists anywhere: loans and lending run on one shared market with a copied real price. Visitors get test money themselves: their own wallet mints test dollars (tUSDG, no value), and Robinhood's and Circle's public faucets give test ETH, the official test TSLA and devnet USDC.
- **The free public city AI desk.** Off unless `LOCAL_AI_LIBRARY_ENABLED=1`. This setting enables both connector and direct free library mode. Anyone can use it; residence is not checked. Limits are 30 shared attempts per UTC day and three per visitor. Connector free jobs require explicit public-question consent and route only to hosts whose owner enabled `freePublicAnswers` (default `false`); free answers create no payment or payout.

## The GPU

The hosted app uses the [outbound Home Node GPU protocol](../home-node/README.md), not a VPN or an inbound home-network connection ([ADR 0013](adr/0013-outbound-home-node.md)). The existing running GPU connector remains compatible; this change does not replace its installed program. Ollama has no authentication and must stay private. The always-on Linux device initiates HTTPS to `https://ledger.stadtstack.eu` and signs polls/results/heartbeats with its local Ed25519 key. The owner's default wake sends a tokenless UDP magic packet locally to desktop MAC `34:5A:60:69:E2:73`, broadcast `192.168.178.255`, port 9 (recorded read-only in the homelab package). Optional Home Assistant invokes only `script.desktop_ai_wake_gpu_host`, with a dedicated non-admin local token; HTTPS is required unless `homeAssistant.DANGEROUS_ALLOW_PLAINTEXT_HTTP_ON_TRUSTED_LAN` is explicitly `true` in the node's JSON configuration.

The connector must be updated alongside this server behavior: respect the existing job `expiresAt` across wake, readiness and explicit model preload, then cap generation at 90 s or the remaining lifetime, whichever is shorter. Paid third-party answers use x402 `upto`: authorize at most `maxOutputTokens × 100` atomic tUSDG, then settle reported output tokens × 100 only after a saved complete answer with `done: true` and `done_reason: "stop"`. Token-limit, incomplete, interrupted or failed answers cost nothing; own compute and free public answers have no payment, payout or receipt. These changes are not claimed released or proven against the real sleeping GPU here.

Saved-request recovery distinguishes an HTTP failure from a saved job failure: an authenticated successful `GET /api/local-ai/requests/:id` returns HTTP 200 with the owned request state, including terminal failure. A missing connector result after the bounded deadline is `interrupted` with `recovery.code: host_result_missing` and no inference charge; the selected host's current `asleep` status only means Ollama is unreachable, not proof that Wake-on-LAN failed. Solana settlement recovery keeps the durable operation link before signing and reports a safe `recovery.stage` and stable error code rather than hiding a saved answer behind a generic 503. Ambiguous settlement remains pending and must be reconciled, never relabelled uncharged or replaced by a new approval. An SPL delegate approval is not payment, has no automatic time expiry, and any remaining finite allowance stays on chain until the wallet replaces or revokes it. The application must not use it to settle a failed/missing answer.

An unsigned Solana approval review has a maximum two-minute **site review policy**, separately bounded by its original blockhash lifetime, which can end sooner. Recovering its canonical expired operation ends that question (`approval_expired`); it does not recycle the expired transaction or claim that an already-granted SPL allowance expired. Starting a new question can hand off the per-wallet lane only after the old approval is proven terminal. An ambiguous signed approval remains fenced and is reconciled before quote-expiry logic can end the request. House reviews display observed confirmed block height, the original inclusive last-valid block height and remaining blocks; no wall-clock duration is presented as blockchain validity. The site policy deadline is labelled separately. A pre-sign canonical check refuses expired or unverified reviews before opening the wallet; background refreshes do not erase an action's failure.

Solana pre-sign verification uses **one finalized `simulateTransaction` response** for native pre/post balances, token pre/post balances, the fee and requested post-account bytes ([RPC contract](https://solana.com/docs/rpc/http/simulatetransaction)). It never reconstructs deltas from another RPC bank; the obsolete cross-request slot-matching loop is removed. Missing atomic evidence fails closed, rather than guessing zero or falling back to mismatched snapshots. Exact atomic debit/credit limits, token owner/mint/program checks, post-token initialized/frozen checks, user native-fee protection and conservative sponsor debit-plus-fee ceilings remain mandatory. A linked but still unsigned AI settlement can resume its existing immutable intent before expiry; it is not a replacement transaction or a second approval. Durable signing leases fence a stale worker at the signed-write boundary and preserve ambiguous signed transactions and their fee reservations.
